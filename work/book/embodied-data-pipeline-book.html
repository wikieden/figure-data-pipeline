前言：为什么要写一本数据管线的书

一个反直觉的起点

2026 年谈机器人基础模型，大家首先想到的是模型：VLM 骨干多大、动作头用扩散还是流匹配、要不要预测下一帧。但把 Figure、Dyna、Generalist、Sunday、Skild、NVIDIA GR00T、某大模型厂商、自变量这些团队公开的做法放在一起看，会发现模型层其实在快速收敛——VLM 骨干加流匹配动作头、统一槽位向量加掩码、相机系增量动作，这几条已经有四五家独立走到了同一处（见第 13 章）。真正拉开差距的，是另一件事：谁能把异构、嘈杂、海量的原始采集，变成对齐的、可验证的、可复现的训练数据，并且让评测结果反过来指挥下一轮采集。

这件事就是数据管线。

本仓库的战略判断（data-strategy-roadmap.md §0）可以压成一句话：机器人数据的瓶颈已经从"采不到"变成"采到的东西对不齐、验不了、用不上"。原始供给——众包第一视角视频、无本体手持设备数据、训练场遥操作——在 2026 年下半年已经过剩，而把它们对齐到同一动作 schema、在段级判定价值、用可校准的评测把数据收益变成成功率，这三件事仍然稀缺。

这本书和仓库其他文档的关系

仓库里已经有五十多份文档：总设计 architecture.md、全链路设计 data-pipeline-design.md、系统规划 data-system-plan.md、各层规范（格式契约、recorder、ingest、策展、评测、训练）、二十多份对他家的调研，以及治理登记。它们按"谁要实现什么"组织，适合查阅，不适合从头读。

这本书按另一条线组织：跟着一条 episode 走完它的一生。它在某台设备上被录下来，带着时间戳和标定上传，在入湖时被校验和对齐，被质检打上各种标记，被切成子任务、写上描述、补上伪动作，可能被拿去合成更多数据，被检索出来放进某个训练配方，变成一份冻结的数据集，被模型消费，再在评测里暴露出某种失败，然后这个失败沿着 lineage 回到采集端，变成下一批采集任务。每一章讲这条路上的一段：做什么、为什么这样做、他家怎么做、我们的规则是什么、还有什么没定。

三条贯穿全书的纪律

读这本书时会反复遇到三条纪律，先在这里点出来：

  1. 清洗是标记不是删除。 raw 永存（隐私脱敏和合法删除请求是唯一例外）。所有质检结论都是追加在数据旁边的列，训练时选用哪一份"视图"，就是选用哪一组标记。这让阈值可以被消融裁决，而不是一次拍板永久生效。
  2. 质量优先于吞吐。 Figure 用 8 小时精策划数据就出了可用策略；GR00T 2 预训练混合里人类视频占约 92%，但真正稀缺的是"对齐过的"小时。所以质检和评测排在采集扩张之前。
  3. 每个判断都要能追溯。 任何一个训练分片都能沿 lineage 追到它的策展决策、所用规则与模型版本、原始上传；任何一个对外的能力宣称都要能指向一个评测 run 和它的日志。引用他家数字时标注来源属性，依赖自报数字的决策登记在案。

关于可信度

这本书大量引用他家数字。行业里的数字有三种：论文里可复现的、公司一手页面上的、媒体转述的。公司对自己产品性能、规模、成本的陈述，即使出自一手页面，也是自报，未经独立验证，书中一律标 ⚠️。我们用这些数字判断方向、给阈值定起点，但不把它们当设计参数——阈值最终由我们自己的消融裁决。

关于现状

截至 2026-11-20，本仓库的代码处于 M1（采集与格式）阶段：schema.py 已到 0.2 并带读侧迁移，其余模块是骨架。所以本书描述的绝大部分是经过推敲的设计，不是已运行的系统。第 17 章列出了按里程碑的建设顺序，以及几个连领先团队自己也没解决的问题。

第 1 章 具身数据的瓶颈在哪里

1.1 具身数据为什么特殊

互联网文本和图像数据的问题主要是"多"：清洗、去重、过滤有害内容。自动驾驶数据的问题主要是"长尾"：常规场景多到泛滥，罕见场景采不到。具身操作数据同时面对这两个问题，还多了三个它们没有的难点：

  1. 动作不在画面里。 一段人做家务的视频，看得见手在动，看不见关节角、末端位姿、抓握力。要把它变成机器人能学的监督信号，必须恢复或合成动作。这是"具身鸿沟"（architecture.md §6）。
  2. 形态各不相同。 同一个"把杯子放进篮子"，可以由遥操作的双臂机器人、戴头戴相机的人、拿 UMI 夹爪的人、仿真里的虚拟手完成。它们的观测视角、动作空间、采样率、噪声来源都不同，却要进同一个模型。
  3. 时间要对得很准。 动作专家以 100–200 Hz 消费状态和动作，一个控制周期只有 5–10 ms。视觉帧和动作差一帧，学到的就是错位的因果。

1.2 供给过剩，可用稀缺

2026 年的态势（data-strategy-roadmap.md §1.2）有一个很清楚的剪刀差：

  • 供给端在崩价。 众包第一视角视频的事实价格约 $6/小时（第三方），Figure Index 官方口径每秒入库 30 分钟视频，Generalist 自报 50 万+ 小时手持夹爪数据 ⚠️。
  • 可用端仍然稀缺。 熟练采集员的有效数据只有 1/3–1/2，QA 拒收 10–30%；Dyna 自报成功率 99.9%，而客户侧质量通过率只有 87% 和 46% ⚠️；Index 的五阶段策展会丢弃大部分原始上传（Forbes，第三方），可用训练数据远小于 1,600 万条的名义规模。

结论是：原始小时不是资产，是输入。CTO 的资源应从"多采"转向对齐、策展、评测三个自研环节，原始供给当作可外购的大宗商品（roadmap §2.1）。

1.3 三层数据结构

GR00T 2 的预训练混合给了一个清楚的分层（gr00t2-trends-analysis.md §0，NVIDIA 一手，比例为自报 ⚠️）：人类视频约 92%、机器人遥操约 5%、UMI 约 2%。把这个比例和 roadmap 的态势判断合起来，数据需求可以看成三层：

层 内容 量级 作用
覆盖层 人类第一视角视频（无动作标签） 10⁵–10⁶ 小时 世界知识、物体与场景多样性、视频预测
对齐层 与机器人对齐的人类/手持数据、遥操作、干预段 10³–10⁴ 小时 任务能力、动作语义
本体层 目标本体的 play 数据 + 少量后训练演示 每本体若干小时 交代"这台机器怎么动、长什么样"

稀缺的不是覆盖层的原始小时，而是对齐层的小时和灵巧手的小时。这决定了本仓库四条采集轨的分工（第 3 章）：human 轨打底，device 轨和 robot 轨做对齐层，sim 轨补长尾、做评测载体。

1.4 五个正在发生的转变

roadmap §1 用十个维度扫描了 2026-06 至 2026-09 的 225 条来源，归纳出几个与数据管线直接相关的转变：

  1. 人类视频成为预训练主轴，机器人数据退为对齐层。GR00T N1.7 加入 2 万小时人类视频，Cosmos 3 的动作中训练集 67% 是人类第一视角（官方）；HumanScale 的等小时对比里人类视频优于遥操作（论文）。
  2. 动作空间、格式、质量标准三线收敛。 至少四家独立收敛到相机系相对末端动作；LeRobot v0.6 把逐帧子任务、进度、奖励列做进标准格式；中国 YD/T 6771-2026 八维数据质量标准 2026-11-01 实施。
  3. "不删只标"从原则变成方法。 π0.7 用元数据条件化吃失败和自主 rollout 数据，Ambient Diffusion Policy 用次优数据在 OXE 上再涨最多 33%（论文）。失败数据是一等公民。
  4. 评测走向分级、序贯与代理，并在产品化。 仿真评测器、世界模型评测器开始与真机做相关性标定，但世界模型评测只在专家动作分布内有效。
  5. 监管把 lineage、同意、脱敏变成交付条件。 欧盟 Data Act、CRA、PLD、机械法规叠层生效，旁观者隐私诉讼出现。

1.5 北极星：新任务上线成本

如果数据量不是目标，什么是？本仓库的北极星指标（roadmap §2.3）是新任务上线成本：让一个新任务在真机上分级得分达到 ≥90% 所需的真机小时数与全成本美元。它同时惩罚预训练弱（要采很多新数据）和策展差（采了用不上）。12 个月目标是 ≤20 真机小时 / ≤$5k（占位值，M2 初用实测曲线重定）。

数据系统对北极星的贡献可以拆成四个直接可管的量（data-system-plan.md §1.3）：

新任务上线成本（北极星）
 ├─ 可用训练小时/月 ········· 入湖量 × 漏斗通过率
 ├─ 每可用训练小时全成本 ···· 采集计酬 + 设备摊销 + 平台 + VLM + 人工
 ├─ 采集 → 可训练时延 ········ 上传完成到 training_ready 的 P50 / P95
 └─ 闭环有效率 ··············· 回流 loop 中评测提升的轮次 / 总轮次

1.6 三个战略控制点

roadmap §2.5 用"三问"检验什么才是值得战略投入的东西：拿掉它，对手的新任务上线成本会不会上升；它是否随每次部署或每季度自动变厚；它能不能用钱买到。通过检验的只有三样：

  1. 评测校准数据：自家本体 × 自家任务的真机↔孪生↔代理三层配对。它定义"什么是好数据"，必须在自家本体上做。
  2. 对齐层语料：人↔机同任务配对集 + 干预段。只有同时拥有本体、任务和采集通道的人能产出。
  3. 数据契约 + 同意/来源图：合规交付条件，一旦成为训练场与 OEM 的交付格式，切换成本落在对方。

看起来像控制点、其实不是的：原始小时数、头戴设备、模型骨干、仿真引擎。它们要么已是大宗商品，要么领先半年就被追平。

1.7 本章小结

  • 具身数据的特殊性：动作不在画面里、形态各异、时间要对得准。
  • 瓶颈已从"采不到"变成"对不齐、验不了、用不上"。

第 2 章 七条贯穿性决策

一条管线能不能长期演进，取决于少数几条"不轻易改"的决策是否选对。本仓库把它们写在 CLAUDE.md 里，偏离前必须先更新 architecture.md。本章逐条讲：决策是什么、解决什么问题、代价是什么。

2.1 管线的五层骨架

先看骨架。数据流分五层，src/fdp/ 的子包与之一一对应，CLI 子命令按层命名：

recorder(采集, MCAP) → ingest(入湖: 校验/对齐/转码) → curation(策展) → export(LeRobotDataset v3) → viz(rerun)
   fdp record             fdp ingest                     fdp curate        fdp export                 fdp viz

2026-11-17 对照某大模型厂商 具身数据链路（入湖 → 质检 → 打标 → 挖掘 → 合成 → 训练评估 → 回流）后发现缺了挖掘、人类视频合成、回流闭环三环。补法是不新增管线层和持久化格式：挖掘与合成作为 curation 层的新阶段，回流闭环作为跨层流程用 lineage 串起（data-pipeline-design.md §0）。

图 P1（引自 data-pipeline-design §1）　全链路：采集四轨 → ① 入湖 → ② 质检 → ③ 打标 → ④ 去重再平衡 → ⑤ 挖掘 / ⑥ 合成 → ⑦ 数据集构建 → ⑧ 训练评测 → ⑨ 回流闭环。

2.2 决策一：双格式

内容：机上采集和原始数据用 MCAP（append-only、耐崩、多流单文件）；训练和发布用 LeRobotDataset v3（parquet + mp4、流式）。二者之间由 export 层转换，不引入第三种持久化格式。

为什么是两种：采集态和训练态的需求相反。采集要的是断电不丢、多路传感器各按原生频率写进一个文件、写入时不需要知道将来怎么用；训练要的是按样本随机访问、列式压缩、社区工具直接能读。一种格式两头兼顾，必然两头都不好。

为什么不能是三种：每多一种持久化格式，就多一条转换路径、一套一致性校验、一处 lineage 断点。GR00T 2 用 Lance 做快照和 QC 视图，我们的判断是 Lance 只作为 LeRobot 之下可选的存储后端评估，不作为第三种格式（gr00t2-trends-analysis.md §4）。

外部旁证：Dyna 在百万小时规模上把 episode 容器从 H5 逐帧 JPEG 换成 canonical MCAP + H.264，并按读取模式分组 topic，自报存储 −68%、样本读延迟 2.9× ⚠️（data-format-contract.md §1.1）。

2.3 决策二：四轨同 schema

内容：robot（遥操作/车队，含动作真值）、human（第一视角视频，无动作标签）、device（UMI 类手持/穿戴采集，硬件动作真值）、sim（仿真 rollout）四条 ingest 轨共用同一个 EpisodeMeta，用 track 字段区分。采集方式是组合不是单选；新增采集形态 = 新增 track 值，不新增 schema。所有模态可空（mask），schema 带版本号，新增传感器不得破坏旧数据可读性。

为什么：如果每种采集形态一套 schema，跨形态混合训练就要在训练侧写 N 套适配；更糟的是，质检、去重、再平衡、lineage 也都要写 N 套。同 schema 加可空模态，让"一条 human 轨 episode 没有动作"和"一条 robot 轨 episode 没有掌心相机"用同一种机制表达：掩码。

边界：合成来源不是采集形态。动捕重定向、神经轨迹、人类视频合成的机器人演示都归 sim 轨，用 source 字段区分（sim-track.md §6）。

2.4 决策三：分层采样率

内容：视觉流 ~10–30 Hz（对齐 VLM / S2 消费），状态和动作流 100–200 Hz（对齐动作专家 / S1 消费），统一 ns 时间戳对齐，不做全局重采样到单一频率。

豁免：device 轨的动作流以传感器原生频率入湖（≥50 Hz，如 VIO 位姿 60 Hz），rate_hz 如实记录，export 不上采；训练取帧时对信号流线性插值。

为什么：全局重采样要么把视觉上采浪费存储，要么把动作下采丢掉高频信息；而且一旦重采样落盘，原始时间信息就没了。保留原生时间戳、只在训练取帧时插值，等于把"怎么对齐"推迟到消费时决定。

2.5 决策四：策展五阶段

内容（对标 Figure Index 的官方披露）：自动质量门 → 欺诈/来源审计 → embedding 去重 → 多样性再平衡 → VLM 分层标注（任务级 + 子任务级指令，事后反推式）。QC 分三级：L1 运动学过滤 / L2 统计过滤 / L3 VLM 语义审计。

两条附则：清洗是标记不是删除，raw 永存（隐私脱敏除外）；阈值改动必须走消融裁决。

为什么是这个顺序：越便宜的检查越先跑，越贵的越后跑、只对通过者跑。第 8 章会展开这个成本金字塔。

2.6 决策五：视频编码

内容：机上 h264 硬编；入湖转 AV1（svt-av1）+ yuv420p；解码用 torchcodec。

一个踩过的坑：yuv444p 会导致浏览器和可视化工具无法解码，所以像素格式被写进了决策层而不是留给实现者。

2.7 决策六：质量优先于吞吐

内容：Figure 用 8 小时精策划数据即出可用策略（官方）。数据质量评估与过滤模块的优先级高于采集吞吐优化；缩放消融切分器（按小时、任务、operator_id）是数据集层的内建能力，不是事后脚本。

为什么切分器要内建：判断"再采 100 小时值不值"的唯一可靠方法是缩放曲线——Figure 以 10/20/40/60 小时切分跑曲线来决定采集预算。如果切分要靠临时脚本，曲线就跑不起来，预算就只能拍脑袋。

2.8 决策七：训练层保守、数据层创新

内容：模型决策只抄 ≥2 家独立验证的共识（VLM 骨干 + 流匹配头、槽位向量 + 掩码、相机系增量动作、两段式动作课程），不自研骨干；数据配方（configs/mixtures/*.yaml）是版本化一等公民，哈希进 lineage。

为什么：骨干领先半年就被开源追平，自研骨干的投入不复利；数据配方、策展规则、评测校准数据才随时间变厚。创新预算放在后者。

2.9 在七条之上的五条候选原则

roadmap §2.4 提出了五条候选原则，尚待在下一次 review 中裁决是否写入 CLAUDE.md。它们已经在多处设计里被当作默认值使用：

  1. 单一动作 schema：所有轨最终对齐到相机系相对末端 + 手部/夹爪状态，具身特异性放在提示和掩码里，不放在动作空间里（U-23 已裁决）。
  2. 段级而非 episode 级：策展、估值、奖励、回流都以段为单位，episode 只是容器。
  3. 评测先于对齐采集：robot/device 轨的新预算必须先有对应的评测任务簇与代理相关性。
  4. 供给外购、对齐自研。
  5. 元数据条件化优于过滤：低质、失败、自主 rollout 数据带标签入训练，由模型学会区分；过滤只针对不可用（同步失败、隐私）与投毒。

注意第 5 条与决策四的"质量门"并不矛盾：质量门产出的是标记，标记既可以用来过滤，也可以作为条件输入。选哪种用法，由训练配方决定，由消融裁决。

3.2 两种采集哲学

四轨背后是两种弥合人→机器人具身鸿沟的对立思路（architecture.md §6.5），本仓库刻意并行两者：

思路 采集端物理消灭 gap：人与机器人共用同一观测-动作接口（腕装鱼眼 + 同款夹爪 + 末端相对位姿动作） 数据端全覆盖，靠算法弥合 gap（手部重定向、光流等中间表征）
泛化保证 由构造保证：训练与部署分布同构，本体不入观测 由模型保证：依赖重定向质量与共训练配方
代价 泛化锚定在"同款末端"；换灵巧手需适配 伪标签精度上限、触觉缺失
任务覆盖 末端能完成的任务子集 全部日常任务
规模证据 Generalist 50 万+ 小时 → GEN-1.5 物理提示涌现 ⚠️ Index 1,600 万条 + Go-Big 导航零样本迁移（官方）

共同点：接口对齐消灭鸿沟，规模多样性提供燃料，二者缺一不可。device 轨和 human 轨的配比不由立场决定，由下游消融裁决——这正是"四轨同 schema、采集方式是组合不是单选"的理论依据。

一个学术旁证：PrimeU（2026-06，论文）显示人类视频零样本迁移依赖人形本体与人类形态的协同设计。Figure 03 的类人形态本身就是 Index 数据能用的前提。

sim 轨是一个"合成来源"的集合，用 source 字段区分（sim-track.md §3）：

3.6 新的采集任务类型：play 数据

GR00T 2 带来的一个重要启发是：目标本体的数据角色正在从"任务演示"变成"本体说明书"（gr00t2-trends-analysis.md §1.3）。GR00T 2 的 X-Adapt 只用目标本体的 play 数据 + 人 / UMI 演示完成适配；当采集器与执行手一一同构时，连 play 数据都不需要 ⚠️。

本仓库据此新增了 play. 前缀的任务模板类型（robot-track-teleop.md §5）：按覆盖计划驱动关节空间与工作空间（含双臂相对位姿、手的全行程、各相机视角下的末端外观），不设成功判据。验收看覆盖度——关节空间各维分箱填充率、工作空间体素填充率、各相机下末端可见帧占比——不看成功率。play 数据在训练配方里单独成组，不进评测集。

3.7 配对采集：对齐层的生产方式

对齐层语料（第 1 章的控制点 2）不是"采更多 robot 数据"，而是同一任务、同一时刻，用两种采集方式同时录。capture-devices-design.md §7 定义了六组配对：

配对 产出 用途
头戴（D2）+ 触觉 UMI（D1）同时佩戴 视觉伪标签 vs 硬件真值 伪标签质量分定刻度
头戴 + 固定第三人称相机 ego + exo 同步对 上身对齐动作块
触觉阵列 + 光学触觉并排 跨传感器配对帧 触觉迁移
遥操作手套（D4）+ 本体复现 人手关节 vs 机器人关节 重定向误差
手机（D3）vs 头戴（D2）同任务 质量差 决定哪些众包任务只能用头戴
头戴脱敏前 vs 后 手部可见率、MPJPE 差 脱敏损伤基准

第一组最关键：它用很低的成本给 human 轨伪标签提供了"标准答案"，比动捕手套方案便宜得多（device-track-umi.md §3）。

  • 四轨分工：human 管覆盖、device 和 robot 管对齐、sim 管长尾与评测。

4.2 末端：采集器与执行手共同设计

GR00T 2 的 DexUMI 与 XHAND 一一对应，Sunday 的手套复刻目标夹爪几何，TwinDEX 让人穿与机器人同构的外骨骼——多家都在走"采集器与执行手共同设计"（gr00t2-trends-analysis.md §3.1）。

本仓库的当前方向是 T/I/S 两节同构手（inhouse-isomorphic-end-effector.md）：独立拇指 T、独立食指 I、后三指合组 S，各两节、加粗、有承载掌面；相机在拇食之间靠背侧，向掌心捏取区看。同一构型同时用于穿戴采集器（device 轨）和机器人执行手（robot 轨）。

这带来了几条数据层的硬要求（data-format-contract.md §1.4，设计待实现）：

  • 单独版本化的末端档案，区分穿戴采集与执行手、左右、两节与历史二指版本；
  • 人体测量、映射目标、实际发出的命令、机器人反馈分别声明来源——穿戴机械读数不是机器人已执行的动作；
  • /video/palm_left/right 表示看抓取区的语义视图；
  • 旧二指数据保留独立身份，不静默替换。

另一个契约级的趋势是：相机布局收敛为"头部 1 路 + 双腕 2 路"，腕部相机安装位成为跨设备契约。本仓库在本体工程冻结时把相机外参写进具身档案 cameras.<name>.mount，作为 D1/D2/D4 支架的共同基准（robot-track-teleop.md §1.1）。

4.3 五件设备的共性规范

不管哪件设备，都要满足同一组共性规范，缺任一层不进 record→export 验收（capture-devices-design §6）：

  1. 时钟与同步总线：单调 ns 时钟 + 启动时记录 UTC 偏移；有线场景 PTP，头戴/手持用硬件触发脉冲 + 同步 LED 事件。
  2. 标定随数据走：出厂内外参 + 时间偏移写进 /meta/calibration，哈希进 EpisodeMeta。
  3. 隐私硬件三件套：硬连线录制 LED（软件不可关）、遮挡或篡改即停录、物理停录开关。
  4. 设备注册：一机一码，固件签名，OTA 灰度，设备档案进 lineage。
  5. 固件落盘即 MCAP 契约：/meta/health 1 Hz、关键帧间隔 ≤1 s、chunk 4 MB/1 s flush、断电可恢复。

还有一条采集 SOP 的共性：每个任务模板附带"扰动-恢复"子任务，专门产出恢复数据。

4.4 recorder 的写入模型

fdp record 是 robot 轨遥操作站、自研头戴设备固件和 device 轨设备的共同录制规范（recorder-sync-and-storage.md）：

  • 单进程 MCAP writer，多生产者经有界队列投递。队列满时先丢低优先级流（预览、健康），再丢高优先级流（动作、视频关键帧），丢弃计数写进 /meta/health。
  • flush 与 fsync：每 chunk 4 MB 或 1 s 先到即 flush；每 5 s 或每个关键帧组 fsync 一次。
  • 分段：2 GB 或 10 分钟切换 part；每个 part 头部重复写 /meta/episode 和 /meta/calibration，任一文件可独立解析。
  • 结束标记：episode 结束写最终 /meta/episode（含 duration_ns）。缺失即表示非正常结束，ingest 会补并打 flag:abnormal_end。

4.5 带宽与存储预算

配置 视频 合计写入
robot 轨：3 路 1080p30 h264 @ 8 Mbps + 200 Hz 状态/动作 + 触觉 24 Mbps ≈ 11.5 GB/h
自研头戴：1440p60 h265 @ 20 Mbps + 2 路灰度 SLAM + 双 IMU 28 Mbps ≈ 13 GB/h
UMI（GoPro 原生） 60–100 Mbps 27–45 GB/h（入湖转 AV1）

写入介质要求持续 ≥20 MB/s（留 5× 余量）。一个班次 4 小时约 52 GB，256 GB 设备存储可撑 4–5 个班次不回传。

环形缓冲的铁律：只有已确认上传（服务端哈希回执）的 part 才可被覆盖；未上传数据占满时停止录制并提示，不覆盖。剩余 <10% 关预览流并降码率一档，<5% 停录。

4.6 断电与崩溃恢复

  • 已 fsync 的 chunk 全部可恢复；未 fsync 的最多丢 5 s；缺失的尾部索引由 ingest 线性扫描恢复。
  • 崩溃后重启：发现未关闭的 part → 写恢复标记、新开 part 续录同一 episode（/meta/segment 记录续接关系），不新开 episode。
  • M1 验收必做：录制中随机断电 20 次，要求 100% 文件可被 ingest 恢复、丢失时长 ≤5 s、无静默数据错位（用已知同步事件验证对齐仍在预算内）。

"无静默错位"这一条最容易被忽略。文件能打开不等于数据对：如果断电导致某路流的时间基准漂了，文件完全可读，但视觉和动作已经错开。所以恢复测试必须用同步事件验证对齐。

4.7 非自研录制端

P0 阶段的手机和 GoPro 不要求机上写 MCAP，只需满足输出要求：视频 + 遥测（GPS 剥离）+ 录制起止 UTC 时间；App 写一份等价于 /meta/episode 的 sidecar JSON（episode_id、session_id、device_id、consent_ref、region、任务模板 id、口令时间戳）；多设备同录时开始和结束各做一次 LED 闪烁 + 拍手。ingest 负责拆流转 MCAP。

4.8 遥操作站与接管打点

robot 轨的遥操作站默认用 Quest 3 手追，接口抽象为 Teleoperator 协议，可替换为 AVP、GELLO 或带力反馈的主从臂（robot-track-teleop.md §2–§4）。三个数据层要点：

  1. 闭环延迟测量：每帧同时记录 command_time（遥操作端发出）与 publish_time（机器人执行），端到端 ≤150 ms，超过标 flag:teleop_latency。
  2. 即时质控：episode 结束即给操作员打分（平滑度、时长、静止占比、是否完成），采集时反馈比事后返工便宜得多。
  3. 接管打点由遥操作站写，不是事后标注：/event/intervention 的 takeover_start / takeover_end / estop / reset，精度 ≤ 一个控制周期（10 ms），带原因枚举和被接管的策略版本。混合 episode（策略自主 + 人接管）是经验后训练的素材，必须保留策略段与人工段的边界。

操作员纪律：每班次 ≤4 小时，每小时强制 10 分钟休息（质量随疲劳下降是 DROID 的经验）。

4.9 本章小结

  • 设备选型看它喂哪个控制点；原始人类视频外购，自采只做对齐与校准所需的量。
  • 采集器与执行手共同设计；腕部相机安装位是契约。
  • 共性规范五层：时钟、标定、隐私硬件、设备注册、落盘契约。
  • recorder 的三条铁律：队列满先丢低优先级、未上传不覆盖、断电后不静默错位。
  • 接管打点在采集端实时写，不靠事后标注。

第 5 章 时间、同步与标定

多流对齐是数据可用性的命门。一条 episode 可以画质完美、动作流畅，但只要视觉和动作差了 20 ms，学到的就是错位的因果。这一章讲本仓库的时间语义、同步手段、误差预算和标定纪律（architecture.md §8）。ingest 校验和 curation 拒收判据都以本章为准。

5.1 两枚时间戳

每条 MCAP 消息带两枚原生时间戳：

  • log_time：写入记录器的时刻；
  • publish_time：传感器或驱动声明的采样时刻。

训练与对齐只用 publish_time。 log_time 只用于诊断记录延迟。理由很简单：写入时刻受队列、磁盘、调度影响，和物理世界里"那一刻发生了什么"无关。

其余约定：

  • 单位一律 ns，int64；episode 内用单调时钟（CLOCK_MONOTONIC_RAW 或等价物），另存一枚"单调→UTC"偏移（started_at_ns），跨设备、跨会话的比较只在 UTC 层做。
  • 视频帧取曝光中点，不取帧到达时刻。全局快门相机直接用；卷帘快门相机记录曝光起止，并在标定文件里声明行读出时间。无曝光信息的设备用 pts − 0.5/fps 近似并标 flag:pts_approx。
  • 遥操作动作另记 command_time（发出时刻），用来量化闭环延迟。

5.2 四种同步手段

手段 适用 可达精度 备注
硬件触发（相机 GPIO 同步脉冲 + IMU 同步） robot 轨多相机、自研头戴设备 <0.1 ms 需全局快门与触发线；自研设备的默认方案
同一 SoC 单时钟域软同步 手机、GoPro 单机 1–5 ms 零额外硬件，视频与 IMU 同源即可
PTP（IEEE 1588）/ 有线 NTP 机器人本体多计算板 PTP <0.1 ms、NTP 1–10 ms robot 轨跨板必须 PTP
事后相关对齐（IMU 角速度 vs 视觉旋转、LED/拍手标记） GoPro + 外部 IMU、多设备同穿戴 1–3 ms 零硬件；ingest 内建，产出对齐残差进 QC

5.3 跨时钟域

每个物理设备是一个时钟域。episode 元数据记录所有参与的时钟域及其对 UTC 的偏移与漂移估计（clock_domains[]：name, offset_to_utc_ns, drift_ppm）。

  • 多设备同录（如头戴 + UMI 同戴）：会话开始与结束各做一次同步事件（LED 闪烁 + 拍手，双设备可见可闻），ingest 据此估计偏移和线性漂移；漂移 >1 ms/min 的会话标 flag:clock_drift。
  • 没有同步事件的多设备会话：用 IMU 角速度 vs 视觉旋转互相关估计偏移（窗口 30 s，搜索 ±500 ms）（ingest-spec.md §3）。
  • 机器人本体：主控为时间主，相机、触觉、遥操作端全部对齐到主控 PTP 时钟；遥操作端走 NTP 到主控，ingest 再用动作-状态互相关校一次。

5.4 同步误差预算

以动作专家 100–200 Hz 消费为约束，一个控制周期 5–10 ms：

流对 预算 依据
视觉 ↔ 动作/状态 ≤5 ms（robot/device）；≤15 ms（human，仅供伪标签） 一个 200 Hz 控制周期内；human 轨无动作真值，要求放宽
IMU ↔ 视觉 ≤2 ms VIO 收敛条件
多相机彼此 ≤1 ms（硬件触发）/ ≤10 ms（软同步，仅允许 human 轨） 立体与多视角一致性
触觉 ↔ 动作 ≤2 ms 接触事件对齐

超预算怎么办：不删除。标 flag:sync_budget_exceeded，从 robot/device 轨训练分片排除，但可以留在 human 轨的消费路径。这是"清洗是标记不是删除"的第一个具体例子：同一条数据对一种用途不合格，对另一种用途仍有价值。

5.5 标定工序与漂移再估计

  • 出厂标定：相机内参 + 相机-IMU 外参 + 时间偏移（Kalibr 标准工序，棋盘或 AprilGrid）。标定文件随设备档案走（device_id → calibration_ref），每条 episode 引用标定版本。
  • 在线再估计：每次 ingest 用 VIO 残差与 IMU-视觉时间偏移估计值和出厂值比对；时间偏移 >1 ms 或外参旋转 >0.5° 的设备进"待重标"队列，其数据标 flag:calib_stale。
  • 规模化纪律：几十台以上设备时，标定一致性成为主要误差源（UMI 规模化的经验）。标定文件哈希进 lineage，任何重标产生新的标定版本，不覆盖。

human 轨众包设备没有出厂标定，内参从视频估计（GeoCalib / DroidCalib 类方法），写入元数据时注明来源为估计值（data-format-contract.md §3.1，契约 0.3 待入项）。

5.6 不重采样

ingest 阶段的对齐只产生偏移与残差元数据，不改数据。所有流保留原生时间戳。训练取帧时的规则（curation-pipeline.md §5）：

  • 信号流线性插值到查询时刻；
  • 视觉流取最近帧，并记录取帧 Δt（fdp.image_dt_ns.<camera>），模型可选消费。

这样做的好处是对齐算法可以升级：bump ingest_version 后重算偏移，原始数据不动。

5.7 本章小结

  • 只用 publish_time；视频取曝光中点；单调时钟 + UTC 偏移。
  • 四种同步手段按场景选；robot 轨跨板必须 PTP，自研设备默认硬件触发。
  • 误差预算以一个控制周期为界；超预算标记、按用途排除，不删除。
  • 标定随数据走、只增版本不覆盖；在线再估计发现漂移就打标。
  • 对齐产出元数据，不改数据；插值推迟到训练取帧。

延伸阅读：architecture.md §8 · ingest-spec.md §3 · capture-devices-design.md §6

第 6 章 数据契约：MCAP、EpisodeMeta 与版本迁移

数据契约是 M1 的核心交付规范（data-format-contract.md）。它定死三件事：机上和原始 MCAP 文件长什么样；EpisodeMeta 每个字段的含义、谁写、何时写；如何映射到训练态。代码 src/fdp/schema.py 是契约的实现，改字段先改契约文档，再改代码。

6.1 MCAP 采集态

文件与分段

  • 一个 episode = 一个或多个文件 <episode_id>.part-<n>.mcap，单文件上限 2 GB 或 10 分钟。
  • 写入参数：chunk 4 MB、zstd level 3、每 chunk 带 CRC，索引在文件尾。
  • 目录：data/raw/<track>/<date>/<session_id>/<episode_id>.part-<n>.mcap。
  • 入湖态按读取模式分组 topic：视觉流一组、本体感知 + 动作一组，各组时间主序写入、组间不共 chunk。这是 Dyna 在百万小时规模上验证过的做法 ⚠️，与分层采样率决策天然一致。

topic 命名

topic 频率 说明
/video/<camera> 10–60 Hz 机上 h264/h265 Annex-B，入湖后 AV1；关键帧间隔 ≤1 s；<camera> 用语义名
/signal/<stream> 50–1000 Hz values: float32[dim]
/imu/<device> ≥200 Hz 加速度 + 角速度 + 温度
/event/intervention 稀疏 接管开始/结束
/event/task 稀疏 任务开始/结束/中止、口令、子任务标记
/event/sync 稀疏 跨设备同步事件
/meta/episode 文件头 1 次 + 结束 1 次 结束那份含 duration_ns
/meta/calibration 1 次 内外参、时间偏移、calibration_ref
/meta/health 1 Hz 自检、丢帧计数、磁盘余量

相机语义名归一化

设备上任意命名，export 时映射到固定词表：head、head_left/right、wrist_left/right、palm_left/right、ego、ego_wrist、third_person、slam_left/right。映射表随设备档案走。

这条看似琐碎，实则致命。SmolVLA 的教训：相机命名不一致会静默毁掉跨数据集训练——模型不会报错，只是把左腕当成右腕学。

6.3 版本迁移

  • schema_version 用 major.minor。minor 升级只允许新增可选字段或放宽约束，必须能无损读旧数据；major 升级允许删字段，但要提供迁移函数并保留旧 reader 一个里程碑周期。
  • 迁移在读侧完成（fdp.schema.migrate(raw) -> EpisodeMeta），MCAP 文件本身不回写；ingest 把迁移后的元数据另存进元数据库，raw 永远保留原版本。
  • 0.1 → 0.2：subtask_instructions 复制到 subtasks（区间为 None）；state 由 curated 推断；其余新增字段取空。
  • 冻结样本 tests/fixtures/episode_v0_1.json 必须永远可读（tests/test_schema.py::test_migrate_v0_1）。

这是本仓库目前已经实现的部分。

第 7 章 入湖：校验、对齐、转码、幂等

入湖（ingest）把上传完成的原始文件变成 state = ingested 的 episode：raw 区对象、元数据库记录、AV1 转码产物（ingest-spec.md）。它是第一道"确定性"关口——没有任何模型参与，只做物理上能判定的事。

7.1 流水线

uploaded ──校验──► verified ──拆流/对齐──► aligned ──转码──► transcoded ──登记──► ingested
   └─(哈希不符/损坏)→ rejected(reject_corrupt)   └─(对齐超预算)→ ingested + flag:sync_budget_exceeded

每一步幂等、每一步产物写 artifacts 表、任一步失败进重试。

7.2 校验

  • 完整性：分片哈希 vs 上传声明；全文件 BLAKE3 → content_hash；MCAP chunk CRC 全量校验；缺尾部索引 → 线性扫描恢复并标 flag:recovered_index。
  • 元数据：/meta/episode 必须存在；human 轨缺 consent_ref / region、各轨缺 device_id / calibration_ref / operator_id → reject_meta。
  • 标定：标定版本必须存在于 devices 表且与固件兼容；否则 flag:calib_unknown——不拒收，但不进 robot/device 训练分片。
  • 时长：<10 s → reject_short。
  • 时间戳单调：任一流倒退 >1 ms → reject_timing。GoPro 类设备已知有抖动，先用 50 条实测分布、阈值取 P99，写进 configs/ingest/thresholds.yaml（R-07）。

注意"拒收"和"标记"的区别：拒收只用于物理上无法使用（损坏、缺授权、时间倒退）；能用但不适合某种用途的，一律标记。

7.3 拆流与对齐

  • 非 MCAP 输入（MP4 + GoPro 遥测、手机 App 的 JSON 遥测）拆成标准 topic 写成 MCAP，原文件同样存 raw 区。
  • 视频帧时间取曝光中点；跨时钟域偏移按第 5 章的方法估计，写 clock_domains[]，残差进 QC。
  • 丢帧：帧间隔 >1.5/fps 记丢帧；丢帧率 >2% 标 flag:frame_drop，>10% reject_frame_drop；信号流缺口 >100 ms 标 flag:signal_gap。
  • 不重采样：所有流保留原生时间戳。

7.4 转码

  • 存档：AV1（svt-av1，硬编优先）、yuv420p、CRF 30、先用 1 s 固定 GOP（ingest 时还不知道子任务边界；分割后按需重切 GOP 是可选优化）。
  • 训练分辨率阶梯（448p / 720p）与预览流在 curation 打包时生成，不在 ingest 做。
  • raw 原编码文件永久保留。

GOP 长度最终要跟着消费方式调：世界-动作模型的长序列可用大 GOP，VLA 的短窗口需要小 GOP（Dyna 的经验 ⚠️）。所以 GOP 是 export 参数，不是存档常量。

7.5 重试、退避与死信

错误类型 例子 处置
可重试 存储超时、GPU 池满、VLM API 限流 指数退避 1→2→4→8→16 分钟，最多 5 次，之后进死信队列并告警
不可重试 哈希不符、schema 无法迁移、损坏无法恢复 直接 rejected，通知上传方（App 显示原因，可重传）
部分成功 转码失败但校验/对齐成功 保留 aligned，只重跑转码

7.6 幂等与增量重跑

  • 幂等键：(episode_id, content_hash, ingest_version)。同键重复触发直接返回已有结果。
  • ingest_version 随对齐算法、阈值、转码参数变化而 bump（configs/ingest/*.yaml 的哈希）。bump 后可对历史 episode 增量重跑：只重跑受影响的步骤；旧产物保留到新产物验证通过后再标过期。
  • 重跑不改 episode_id，只写 artifacts 与 decisions 的新行。

幂等是可重放的前提，可重放是"阈值可消融"的前提。如果重跑一次 ingest 会产生新的 episode_id，那么 lineage 就断了，任何"换一组阈值再试"的实验都无法和旧结果对比。

7.7 断点续传

  • 上传分片 8 MB，每片带哈希；服务端记录已收分片集合；客户端可从任意分片续传；整文件哈希通过才触发 ingest。
  • 多 part 的 episode 要所有 part 到齐才进 ingest；超过 24 小时未到齐，标 flag:incomplete_parts 并以已到 part 入湖——不等永远。
  • 预览流先行：320p 预览流先上传、先跑技术门 + 视觉门快筛，不通过则通知 App 停止上传存档流。对众包来说这一条省下的带宽相当可观。

7.8 采集规则快照绑定

这是 2026-11-17 对照某大模型厂商链路后新增的一条（data-pipeline-design.md §3）：每个采集任务下发时冻结两份规则文件，并把哈希写进该任务下每条 episode 的元数据。

  • collection_rule：标准步骤序列、允许的物体与场景、必需的流和相机。质检的流程指标（步骤覆盖率、顺序匹配率）和打标的边界先验都从这里读。
  • quality_rule：该任务适用的质检阈值版本与状态机。

目的：规则改了，旧结论仍能对应到当时的规则。 否则半年后有人问"这批数据当时为什么判 pass"，没人答得上来。提议位置 configs/qc/collection_rules/<task>.yaml、configs/qc/quality_rules/<version>.yaml，改动 = 新版本，哈希字段随契约 0.3 入 schema。

7.9 验收

  • 单测：损坏 MCAP 恢复、合成数据已知偏移的时钟估计、丢帧统计、幂等重入。
  • golden fixture：一条 10 s 合成 episode（三路流 + 已知偏移），输出与预期元数据比对。
  • H0 首批 100 小时数据 ingest 通过率 ≥90%，被拒原因分布可解释。

7.10 本章小结

  • ingest 只做确定性的事：校验、拆流、对齐（只产元数据）、转码、登记。
  • 拒收只给物理上不可用的；其余标记。
  • 幂等键 + 版本化配置 = 可增量重跑 = 阈值可消融。
  • 采集规则快照让质检结论可复现。

第 8 章 质检：清洗是标记不是删除

质检是整条管线里唯一能在没有模型、没有本体的阶段就产生价值的环节，所以它最先交付（规则段随 M1，语义段与报告段随 M2）。这一章讲质检的状态机、成本金字塔、各道门、按轨的检查矩阵，以及把质检做成"交付物"的方法。

8.1 episode 状态机

raw ──技术校验──► ingested ──质量门L1──► gated ──L2/L3──► scored
     └─(拒收:损坏/不完整)         └─(flag:reject_*)      │
                                                        ▼
training_ready ◄──打包── labeled ◄──标注/伪标签── segmented ◄──分割──
      │
      ├──► 训练分片（LeRobotDataset v3）
      └──► 演示库（3–12s 切片，按任务 embedding 检索）

每个 episode 携带 quality_flags（拒绝或降级的原因码）与 quality_score（0–1 合成分）。状态迁移全部落 lineage：谁（哪个 worker、哪个模型版本）在何时基于什么规则做了什么决定（curation-pipeline.md §0）。

8.2 为什么是"标记不删除"

三个理由：

  1. 阈值会错。 v0 阈值大多取自他家自报数字，没经我们的数据验证。如果按错的阈值删了，就再也找不回来。
  2. 同一条数据对不同用途价值不同。 同步超预算的 episode 不能进动作专家分片，但能进 human 轨预训练；手部可见率低的 episode 不能做操作监督，但能做导航预训练。
  3. 失败数据有用。 "元数据条件化优于过滤"（第 2 章）：失败、次优、自主 rollout 数据带标签进训练，模型学会区分。

唯一的破坏性操作是隐私脱敏（人脸模糊不可逆），以及合法删除请求。

8.3 成本金字塔

cleaning-algo-selection.md §0 给出的级联原则：每层淘汰后才进下一层，单位成本差 1–2 个数量级。

第1层 规则/传统 CV     全量, CPU, ~0 成本    （ffprobe、直方图、Laplacian、IMU 积分）
第2层 轻量专用模型     全量, GPU 批处理      （检测器、轻 CNN）
第3层 重模型          通过者/抽样           （SLAM、手部姿态、光流、embedding）
第4层 VLM             抽样/仲裁            （语义审计、标注、分歧仲裁）

三条选型原则：

  1. 判据物理明确的，传统方法优先（曝光=直方图、抖动=IMU 积分、时间=校验规则）。AI 在这些场景不是更准，只是更贵。
  2. 判据是语义的，AI 必须上（是不是目标任务、摆拍、手在不在画面）。
  3. 合规场景用最强模型，不省钱。隐私脱敏漏一张脸的代价是法律风险，选型标准是召回率。

8.4 三段执行

某大模型厂商的质检把同一件事拆成三段（data-pipeline-design.md §4.2），我们照此组织：

段 内容 计算 原则
规则段 文件完整、可解码、时间戳与丢帧、多路同步、模糊/过曝/过暗/黑屏冻结、运动学门、统计门 CPU，确定性 明显损坏的在这里拦截，不送入任何 VLM 调用
语义段 遮挡/畸变、手与交互物可见、无效动作、异常静止、步骤覆盖与顺序 VLM，先粗后细 只对粗筛圈出的候选段细检；输出过 schema 校验
报告段 合并、去重叠、判定状态、写报告 CPU 报告只读汇总结果，不重新计算

8.5 规则段的各道门

技术门（入湖即跑）

文件完整、时间戳单调与对齐残差、时长与帧率、元数据完整、隐私（人脸检测→模糊，GPS 剥离）。临时值：相邻帧间隔 >100 ms 记为异常；多路相机算同步覆盖率 = 各路交集时长 / 最长一路。

视觉门

  • 清晰度：Laplacian 方差 <100 记为模糊帧（临时值）；
  • 曝光：亮度 ≥235 的像素占比 ≥80% 为过曝帧，≤16 的占比 ≥80% 为过暗帧（临时值）；
  • 抖动：有 IMU 用 IMU 角速度积分，纯视频用稀疏光流；
  • 内容有效性：黑屏/冻结帧、镜头遮挡、朝天花板占比；
  • 手部可见率（human/device 轨）：<60% 不拒，降级路由到导航或预训练轨道。

上述临时值取自云厂商已交付的 Ego 采集质检（公司自报 ⚠️），只作 v0 起点。

运动学门（L1）

robot/device 轨：目标机器人 IK 可行性（人手能到、机器人到不了的段标记不可重定向）、自碰撞、速度/加速度/jerk 离群（>99.9 分位截断）、静止占比 >70% 降级。

样本窗口判定（human 轨，L1）

这是 2026-11-18 从 GR00T 2 回灌的一条重要改动（curation §1.3b）：human 轨不按整段 episode 判，而是按训练样本实际读取的时间窗判。对每个候选样本起点，取覆盖其观测历史和动作目标的窗口，窗口内全部通过才把这个起点标为合格。这样一段 episode 里只有局部头动过猛或手出画的部分被排除，其余照常可用。

信号 窗口统计 临时值（GR00T 2 自报 ⚠️）
头部角速度 均值 ≤20°/s
头部平移速度 均值 ≤0.2 m/s
手骨长误差 最大 ≤0.05
手可见性 最小 双手都在画面内（单手任务放宽）
腕速度 最大 ≤1.0 m/s

窗口长度跟着训练配方的观测历史和动作块长度走，配方变了就重算——这是第 12 章"QC 视图"的来源。

统计门（L2）

与同任务集群比较：时长、平滑度、工作空间覆盖的分布位置，尾部 1% 人工复核。目的是抓"单条看正常、放进群体看异常"的样本——比如某台设备的速度普遍偏高，多半是标定坏了。

跨模态一致性门

两个某大模型厂商清洗管线实战验证过的门（curation §1.4b）：

  • 指令-动作一致性：标注说"拿起杯子"但夹爪从未闭合→标记；
  • 视频-状态一致性：画面里手在动而状态流静止→时间错位或传感器故障。

8.6 语义段：先粗后细的 VLM 漏斗

  • 粗筛：整段按约 20 s 窗口、5 s 重叠、约 2 s 取 1 帧，拼成联系图（如 5×2）交给 VLM，判断任务与场景是否匹配，并圈出候选段。
  • 细检：只对候选段（前后各扩约 3 s）按 max(0.5 s, 时长/20) 采样约 20 帧细推理；输出必须过 schema 校验，失败重试。
  • 三问：做的是不是声明的任务？是否实际完成？是否摆拍或无实质操作？输出 task_match / completed / staged 三个布尔 + 置信度。
  • 流程指标（任务带标准步骤序列时）：步骤覆盖率 = 观察到的步骤 / 标准步骤；顺序匹配率 = 最长递增子序列长度 / 标准步骤数。没有标准序列的任务不计算，不得用 0 填充。
  • 抽检率随 Creator 信誉浮动：新账户 100%，高信誉 1–5%。

漏斗参数（窗口、重叠、扩边、采样点数）都是消融参数，进 configs/。

8.7 device 轨的三级执行

GR00T 2 的 UMI 数据按"采集站侧自动检查 → agent 打分 → 人工对金标准审计"三级过滤，合计滤掉约四分之一（站侧约 11%、agent 约 16%，自报 ⚠️）。我们的对应（data-pipeline-design §4.2）：

  • 站侧：帧时序不均、丢帧、跟踪或夹爪故障在采集端当场拒绝、当场重采；结果写 /meta/health，入湖时规则段复核。
  • agent 打分：四个方面——任务完成、动作质量（无微调、抖动、犹豫）、场景有效性、视角质量（每路相机都能看到夹爪和任务区）。任一致命失败或低分即拒。
  • 人工审计回灌：抽样复核 agent 判决，对照金标准集，纠错结果回灌为 judge 的训练样本——质检模型本身也要被质检。

8.8 反欺诈：账户级，与 episode 级并行

按分钟计酬必然催生刷量，所以欺诈检测是一等公民（curation §1.6）：

  • 设备指纹 + 时空一致性（同设备不可能同时在两地）；
  • 回放攻击：屏幕翻拍检测（摩尔纹、边框）、同内容跨账户 embedding 碰撞；
  • 激励层防御：计酬锚定"通过策展的分钟数"，而不是上传分钟数；
  • Creator 信誉分 = 历史通过率与审计结果的指数滑动平均；
  • 红队：平台方每月自己制作 ≥100 条已知欺诈样本混入正常流量，检出率即漏检率的度量，SLO ≥95%（data-platform.md §5）。

8.9 四维 × 四轨检查矩阵

某大模型厂商的框架是四个质量维度 × 四种数据形态，映射到我们的四轨，并把"标注本身"单列一列（data-pipeline-design §4.1）：

维度 robot human device sim 标注
完整性 本体型号与频率、多视角流、关节/末端/夹爪状态、干预事件 流完整、无丢帧、估计内参已写入 鱼眼视频 + IMU、夹爪标定、SLAM 轨迹连续 随机化配置哈希、种子可追溯 帧级索引对应、边界与描述齐全
有效性 画质、双臂无冲突、静止占比、任务成功 画质、手部可见率、静止占比 SLAM 位姿与尺度一致、开合误差、重定位漂移 物理合理、渲染有效、增殖成功 边界精度、指代正确率、无幻觉

8.10 质检产物：做成交付物

  • episode 质检报告 quality_report.json：采集指标、各路相机体检、候选段与序列评估、每项指标的分子分母、判定（pass / flag / reject 及原因码）、所用 quality_rule 与模型版本。
  • 批次汇总 summary.json：按批次和任务汇总通过率、主要拒因、需重采的序列数，给采集运营和供应商验收。
  • 指标进元数据库：每项指标一行，供漏斗仪表盘和阈值消融使用。

报告有两类读者：内部（漏斗、消融）和外部（采集供应商验收、PL3 策展即服务的客户交付）。所以报告格式要稳定、带版本号、字段只增不删。

8.11 阈值由谁裁决

所有阈值的最终裁判是下游消融（curation §7）：同批数据不同阈值切子集 → 小模型训练 → 仿真基准分。指标不涨的严格化一律回退。 在消融工具（M3 的 mixture-runner）交付前的过渡方案：阈值取写死的临时值并版本化，各门只标记不删除，记录漏斗通过率，等工具就绪后回溯裁决（U-16）。

漏斗本身也要被监控：单门通过率周环比变化 >20% 触发人工检查——多半是阈值或模型漂移了，而不是数据突然变好或变差（data-platform.md §4）。

8.12 本章小结

  • 状态机 + 原因码 + 合成分，迁移全落 lineage。
  • 标记不删除：阈值会错、用途不同、失败有用。
  • 成本金字塔：规则全量、轻模型全量、重模型抽样、VLM 仲裁；损坏样本不进 VLM。
  • human 轨按样本窗口判，不按整段判。
  • 质检模型也要被质检；反欺诈靠激励设计 + 红队。
  • 质检报告是交付物：分子分母可查、版本化、字段只增不删。
  • 阈值由消融裁决，严格化不涨就回退。

第 9 章 分割与标注：先定边界，再写描述

一条 episode 要变成训练样本，还需要两样东西：时间上的结构（它由哪几个子任务组成、每段从哪到哪）和语言上的描述（每段在做什么）。本章讲这两件事怎么做、怎么验收、怎么让它们变成可重算的派生物。

9.1 三级切分

层级 定义 用途
session → episode 一次任务尝试 策展与训练的基本单位
episode → segment（子任务段） 按子任务边界切 子任务级指令、段级策展、奖励
segment → clip（切片） 3–12 s 干净片段 演示库（物理提示、少样本适应）

session → episode 的起止信号优先级：App 显式标记 > 语音口令（"开始""完成"）> 静止检测兜底。

9.2 子任务边界：按可靠度排序的四种信号

curation-pipeline.md §3.2：

  1. 硬件事件锚点（device/robot 轨首选）：夹爪开合沿、接触力突变——物理事件是最干净的边界；
  2. 手-物接触事件（human 轨）：手部关键点与物体检测框的接触与分离；
  3. 运动学分割：末端或手部速度极小值点（动作单元之间必减速）；
  4. VLM 时序定位：给 VLM 整段视频输出子任务时间戳（多个冻结基础模型投票）——最灵活也最贵，用于校正前三者。

融合策略：1–3 生成候选边界，4 做语义合并与命名。边界精度要求"秒级"，不追帧级。

用 VLM 切边界时的两条经验：先整段粗分，prompt 里写明"只切完成事件"，不给清单和粒度先验；再在粗边界附近开窗局部精修，不外扩窗口。

9.3 先定边界，再写描述

这是从某大模型厂商链路学到的一条关键纪律（curation §3.2）：边界和描述两步解耦。边界错和描述错的原因不同，混在一次推理里没法分别诊断。写描述时只在已固定的边界上写，不得移动边界。

边界确定之后跑确定性后处理（纯代码，规则版本化）：吸收过短碎片、合并相邻同类动作、边界吸附到硬件/接触/速度信号的最近事件点、修复相邻段的空隙与重叠。

9.4 已知失效模式

他方实测（自报 ⚠️）的几种典型失败，是我们评测集要专门覆盖的切片：

  • 欠分割为主：大量段超过 10 s；
  • 模型间共识低：严格 IoU ≥0.75 的只有约三成；
  • 短动作切不出：短于 2 s 的动作基本切不出来；
  • 人工标注也不可靠：约四成人工标注段需要复核。

三种采集形态的难点不同，规则按轨分开调：device 轨是设备入画、抖动、边界难定；human 轨是没有空间锚点、动作短而密；robot 轨是空闲段多、任务模板化、错误容易被批量复制。

9.5 两把尺子

分割器验收同时报两把尺子（curation §7）——因为同一对模型，宽松口径差 2.7 倍，严格口径差 7.5 倍（某大模型厂商单视频实证 ⚠️）。只报宽松口径会掩盖欠分割。

  • 宽松：切点级 boundary F1，边界落在容忍窗口（起步 0.3–0.5 s）内即命中；
  • 严格：整段 IoU ≥0.75 才算配对，一对一匹配，禁止一对多；
  • 另报：预测段数 / GT 段数之比、平均段长。

GT 用两套：sim 轨 planning_trace 的谓词真值（零成本、精确），和人工金标准。评估口径不得奖励"切得粗"——一对多匹配要记为错误，而不是丢弃。

9.6 分层语言标注

  • 三级：任务级（整段一句）/ 子任务级（每段一句）/ 操作级（动词短语，可选）。
  • 事后反推式 prompt（Figure 原方）："你会给机器人什么指令，才能得到这段视频里的行为？"
  • 轨迹投影叠加（某大模型厂商技巧）：标注前把手腕或末端轨迹投影叠加到采样帧上，让 VLM 能"看见"运动而不只是静帧。
  • 采集端事件随片段下传：失败、重拍、换道具、中止（来自 /event/task）必须随片段送到标注端，不能只给一个 mp4。

三条描述规则（自 GR00T 2 Flora 回灌）

  1. 失败的尝试按意图描述，不暗示成功："试图把杯子放进篮子"，而不是"把杯子放进篮子"。成败另存为结果槽位。否则失败段会以成功指令进训练。
  2. 双手并发的不同动作保持为两个独立区间，不合并成一句，各自标明是哪只手。
  3. 描述一个区间时可以看前后相邻帧来确定物体身份和意图，但描述只写目标区间本身。

9.7 槽位化：描述不是一句自由文本

描述按槽位结构化存储：动作、操作对象、目标位置、结果状态，加上子边界与边界判据（硬件事件 / 接触 / 速度极小值 / VLM / 人工）。好处：

  • 粒度调整、模板变更时用离线重映射生成新描述，不重标；
  • 抽检可以按槽位分别统计错误率。

错误主要出在指代上——容器、目标位置、结果状态——而不是动词。同一 episode 内一处指代错误会连续复制到后面多段。所以抽检和交叉校验优先盯这几个槽位；也要防止把 episode 级任务名直接当成子任务描述。

9.8 一致性防线

  • 双模型交叉标注：本地 Qwen-VL + 外部 API，分歧样本进人工队列；
  • 形式违规（字段缺失、格式不符）由自动校验修正或重试，不进人工队列；
  • 对齐度检查：指令与视频 embedding 的 CLIP 分数过低→重标。

标注不一致比标注缺失更伤下游（DeMiAn 结论，论文）。

9.9 按用途定义标注档案

同一份视频，用途不同，要的标注不同，验收口径甚至互相矛盾（某大模型厂商自报：粒度与用途不匹配，训练效果下降 60% ⚠️）。所以标注按档案产出（data-pipeline-design.md §5.1）：

档案 消费方 边界要求 描述要求 验收重点
action_expert 动作专家（S1） 帧对齐，与连续轨迹一致 动词短语即可 严格 IoU 尺子、伪动作质量分
planner 规划器 / S2 语义边界（子任务完成事件） 槽位齐全，指代准确 指代正确率、指令可执行性
pretrain 0→1 预训练 覆盖面优先于精度 任务级 + 子任务级一句话 覆盖率、宽松尺子

档案是 export 的输入参数，不是三份独立标注：底层存同一份槽位化标注，按档案在导出时组装。新增或修改档案 = 改配置版本，靠离线重映射生成，不重标。

9.10 规范版本管理与待裁决队列

  • 标注规范是版本化文件（提议 configs/annotation/spec/<version>.md + 机器可读规则 .yaml），每条标注记录所用规范版本。
  • 规范待裁决队列：规范没有覆盖的情况——"接近算不算一段""微调算不算""空闲归谁""双手同时动怎么表达"——不强迫模型或审核员当场给答案，而是进队列；裁决结果回写规范、产生新版本，再离线重映射受影响的已有标注。
  • 目标是把规范逐步从"人能读懂"变成"机器可判定"：每条规则要么能被确定性后处理执行，要么能被自动校验检查，否则它就是待裁决项。

9.11 标注引擎化

GR00T 2 用 Flora 三模型（切分 / 描述 / 奖励）两天重标约 40 万小时 ⚠️，人只负责最优样本和金标准（gr00t2-trends-analysis.md §2）。这意味着三件事：

  1. 标注是可重算的派生物。规范、模型和版本管理比标注量重要；manifest 要钉住标注版本。
  2. 用可验证奖励训标注模型。两把尺子和指代正确率不只是验收指标，也可以作为标注模型的奖励；金标准集与 held-out 分开。
  3. 奖励标注与语言标注同源。同一个引擎产出结果奖励、稠密进度、rubric 分项，直接喂 RL 和评测（契约 0.3 的奖励列）。

人在环的方向因此是：从"从零标"到"只改错"，再到"只看风险分级后的高风险片段"。人工改错按 SFT 语料格式存，回灌标注模型。

9.12 打标评测集

  • 每条轨、每个档案各维护一套金标准小集（几十条 episode 量级，按任务分层），两名以上标注员独立标注并裁决；
  • 指标：两把尺子、段数比、平均段长、指代槽位正确率、描述幻觉率；
  • 任何打标模型、prompt、后处理规则或规范版本的变更，都先在金标准集上回归，不退步才上线。

外包标注的计价不能按段数或按时长单独计：前者诱导多切，后者诱导少切（curation §9）。

9.13 本章小结

  • 边界信号按可靠度排序：硬件事件 > 接触 > 速度极小值 > VLM。
  • 先定边界再写描述；确定性后处理版本化。
  • 两把尺子同时报，评估不奖励切得粗。
  • 描述槽位化，错误盯指代；失败按意图描述。
  • 标注按档案组装，规范版本化，未覆盖情况进待裁决队列。
  • 标注引擎化后，标注是可重算的派生物；任何变更先过金标准回归。

第 10 章 伪标签、具身转换与合成

human 轨的视频没有动作，device 轨的穿戴子形态把人体拍进了画面，机器人数据又贵又少。这一章讲三种把"不能直接用"变成"能用"的处理：伪标签工厂、具身转换、合成。它们的共同纪律是：产物是派生 episode，parent_episode_id 指回原始，raw 永存，失败是标记不是删除，所用模型版本与权重哈希进 lineage。

10.1 具身鸿沟的三种跨法

做法 输入 动作来源 适用
伪标签工厂 human 轨视频 从视频恢复手部位姿 → 末端 → 重定向 覆盖层数据进动作监督
具身转换 device 轨穿戴/头戴子形态 硬件真值 人体入画的穿戴设备
人类视频 → 机器人演示合成 human 轨视频 + 伪标签 伪动作经重定向 + IK 把人的视频变成"机器人在做"的视频

此外还有不依赖人类视频的合成：仿真增殖和世界模型生成（§10.5）。

一个背景判断：潜动作模型（LAPA 式）在操作任务上表现差（MetaWorld 0.14 vs 光流中间表征 SOF 0.69，论文），光流、重定向这类显式中间表征目前更可靠（architecture.md §6）。

10.2 伪标签工厂

curation-pipeline.md §4.2 的六步：

  1. 手部关键点：HaMeR / WiLoR 级模型逐帧初值；
  2. 整段时序优化：骨长恒定 + 关节限位 + 速度上限约束 + Savitzky-Golay / SLERP 平滑；遮挡帧标插值；
  3. 相机位姿：VIO/SLAM 解出世界系，先解自运动再解手；
  4. 末端化 + 逐形态重定向：FK 感知，保持腕与指尖的任务空间几何；
  5. 中间表征：光流（必做）、单目深度（可选）；
  6. 质量分合成 = 模型置信 × 多视角一致 × 时序一致 × 物理合理 × 误差预测器。

质量分怎么验证

第 6 步的乘积公式本身要被验证：在金标准配对集上算"质量分 vs 真实误差"的 Spearman 相关，<0.5 就回退到单因子（只用误差预测器）。金标准配对集来自第 3 章的配对采集——头戴设备与 UMI 同时佩戴，得到"纯视觉伪标签 vs 硬件真值"。

指标：MPJPE（mm）、末端位置 RMSE（mm）、姿态 RMSE（°）、开度 MAE。算法升级必须先过金标准回归。

骨长误差的双重身份

样本窗口判定里的手骨长误差（第 8 章）同时是伪标签质量信号：一段持续超限通常意味着手部重建失败，进质量分而不只是过滤。

伪动作的上限

GR00T 2 的人类视频收益主要来自视频预测损失，动作损失依赖手部位姿精度，这层精度在我们这里还没有基线（gr00t2-trends-analysis.md §5）。人类视频还丢了主动感知；生成视频"几何幸存、控制信号丢失"。伪动作能撑多深的任务，是本书最后一章的开放问题之一。

10.3 具身转换（可选阶段）

UMI 式手持夹爪靠腕装鱼眼保证"本体不入观测"，无需转换。但穿戴孪生手套（Sunday 式）和穿戴外骨骼（TwinDEX 式）走头戴观测，人体手臂会入画，且各采集员运动学不一。对这类子形态，在 ingest 与 curation 之间插入可选的具身转换阶段（architecture §2.3）：

  • 输入 device 轨原始 episode，输出机器人域 episode：人体抹除 + 机器人臂合成 + 跨采集员运动学归一化；
  • 配方对标 厂商论文 六步与 Sunday 的 Skill Transform（Sunday 自报 90%+ 成功率 ⚠️）；
  • 触发条件由设备档案决定；human 轨不走这一阶段；
  • 失败标 reject_embodiment_transform。

10.4 人类视频 → 机器人演示合成

这是 2026-11-17 新增的一环（data-pipeline-design.md §7.2），对标 厂商论文 与某大模型厂商预处理管线的六步：输入 → 重定向与平滑 → 手臂分割 → 人手擦除与修复 → 底座搜索 + IK → 深度引导的机器人合成。他方规模：1,933 小时人类视频生成 15 种本体共 24,808 小时演示（≈12.8×，论文，口径见 D-11）。

我们的规则：

  • 前置条件：输入必须已经通过伪标签工厂，质量分达到门槛；IK 门标为不可重定向的段不进合成。
  • 归属：观测是部分生成的、动作是伪标签，按 sim 轨判据提议归 sim 轨，source = human2robot_composite，parent_episode_id 指回 human 轨原始（U-47 待裁决）。不新增 track。
  • 合成专属 QC：人手擦除残留（检测器在擦除后的帧上仍检出手）、机器人臂与场景深度遮挡关系一致、合成臂姿态与动作逐帧一致（渲染姿态反投影误差）、IK 可行与自碰撞。不过的标 reject_synthesis_*。
  • 与具身转换共用代码（curation.synthesis）：两者流程同构，都是"抹人 + 合成机器人"，区别只在输入轨和动作来源。
  • 本体档案：每种目标本体一份合成档案（URDF/网格、相机安装位姿、可达空间），版本哈希进 lineage。第一批只做自己的本体和二指兼容视图，不追求 15 种。

10.5 仿真增殖与世界模型生成

仿真增殖（sim-track.md §3）：DexMimicGen 从每任务 10–50 条种子演示增殖 100–1000×；SimFoundry 用 10–15 条种子 + MimicGen + 域随机化做到零样本迁移，物体表亲在 held-out 物体上 +50 点（论文）。增殖成功判定（DexMimicGen 自带的任务成功检查）必须为真才入 training_ready。

域随机化版本化：光照、纹理、物体位姿分布、相机抖动、动力学参数写在 configs/sim/randomization/<name>.yaml，哈希进每条 sim episode。

资产纪律：MJCF 是唯一手写源，USD 与 URDF 一律由 MJCF 生成、不手改、不反向转换——因为 URDF → MJCF 会丢掉最影响接触的参数（每个 geom 的摩擦、solref/solimp）。

世界模型生成（data-pipeline-design §7.3）：候选有 厂商世界模型、厂商合成模型、Cosmos 系列，受 license 准入规则约束，效果均为自报 ⚠️。用途优先级：评测代理 > 长尾补充 > 数据增殖。世界模型只在专家动作分布内可信，所以生成数据只补长尾，不当主力。神经轨迹必须经 IDM 打伪动作并标质量分。

10.6 合成的触发与配比

  • 合成不普遍铺开，由挖掘结果驱动：再平衡的稀缺簇、回流闭环的数据缺口决定合成什么、合成多少（第 11、14 章）。
  • 合成数据在配方里按 source 单独成组设权重，配比由缩放消融裁决。
  • 评测集永不包含合成数据；种子来自 held-out 的 episode 不得用于合成——泄漏规则的延伸。

10.7 闭源合成模型的风险

某大模型厂商的合成模型以"闭源权重 + 受保护联合训练"交付：客户数据只读授权给平台、不可导出，训练后的模型按需导出或限定在其云上部署。这和"raw 永存、lineage 可追溯、删除可传导"冲突（R-27）。采用前必须确认三条：

  1. 合成数据和用它训出的权重归谁、能否导出到我们的存储与训练栈；
  2. lineage 能否记录合成模型的版本与权重哈希（至少要有不可变的版本标识与调用记录）；
  3. 删除请求能否传导到对方平台上的副本。

任何一条不满足，该合成来源只进研究分支。

10.8 本章小结

  • 伪标签工厂六步，质量分本身要用金标准配对集验证。
  • 具身转换只给人体入画的穿戴子形态；human 轨走独立的合成支路，产物落 sim 轨。
  • 合成专属 QC 看擦除残留、遮挡一致、姿态一致、IK 可行。
  • 世界模型优先做评测代理，生成数据只补长尾。
  • 合成由挖掘驱动、按 source 成组、评测集永不含合成数据。
  • 闭源合成平台的三问不过，只进研究分支。

第 11 章 去重、再平衡与挖掘

质检回答"这条数据能不能用"，标注回答"这条数据是什么"。这一章回答两个更靠近训练的问题：这些数据放在一起，分布对不对？ 以及 我要找某类数据时，能不能找到？ 前者是去重与再平衡（策展五阶段的门③④），后者是挖掘（2026-11-17 新增的一环）。

11.1 去重

  • embedding 选型：SigLIP 帧特征聚合（Apache-2.0）起步；InternVideo2 / VideoMAE V2 类视频级表征在 license 核查通过后升级（cleaning-algo-selection.md §1.9）。
  • 两层阈值：近重复（余弦 >0.95，同机位同任务重复录制）→ 保留质量分最高的 1 条；语义重复（0.85–0.95）→ 不删，参与再平衡降权。
  • 同人去重严、跨人去重松：跨人的"相似"本身就是操作者多样性。

11.2 再平衡

  • 对 curated 池按（任务 × 物体 × 环境 × 操作者）四轴聚类：前三轴用 embedding + HDBSCAN，操作者轴直接用 operator_id。操作者轴的依据是 Lin 幂律：场景、物体、操作者数是要扩的三个维度（论文）。
  • 多样性 KPI：每 1,000 可用训练小时的独特任务 / 物体 / 环境 / 操作者数。Index 自报每 1,000 小时 373 任务 / 1,146 物体 / 116 环境 ⚠️，但分母口径未公开，不直接对比（D-09）。
  • 稀缺簇 → 生成任务配额下发 App（主动采集）；过剩簇 → 采样降权（被动平衡）。
  • 训练分片构建时按簇做温度采样（稀缺簇过采样），温度是消融参数。

GR00T 2 给了一个补充视角：配比按"稀缺度"而不是按小时，任务多样性靠工程生成（gr00t2-trends-analysis.md §1.4）。我们据此提议把"技能 × 物体"网格填充率加进多样性计数（行动清单 #9，M3）。

11.3 挖掘要解决的问题

原设计里，演示库的"按任务检索"只有一句话。对照某大模型厂商链路后，挖掘被定义为一个完整环节（data-pipeline-design.md §6.1）：

用途 输入 输出
演示库检索 自然语言或示例片段 3–12 s 干净切片（in-context 演示、少样本适应）
难例 / 长尾挖掘 失败模式描述、少量示例 存量中相似片段 → 补标、重加权、合成种子
技能原语盘点 原语词表 每个原语的小时数、场景数、操作者数
按查询建训练集 保存的查询 + 过滤条件 冻结的片段清单（进 manifest）
评测失败反查 评测失败片段 训练集中相近样本的分布（是缺数据还是数据有错）

最后一项是回流闭环的诊断入口（第 14 章）。

11.4 检索架构：过滤 + 召回 + 精排

查询（文本 / 片段 / 混合） + 结构化条件（track、任务、手别、成败、质量分层、split）
   │
   ├─ 结构化过滤：元数据库（Postgres），先缩小候选集合；held-out 默认排除
   ├─ 召回：片段级 embedding（子任务段 + 演示库切片两种粒度），向量库 Top-K
   └─ 精排：交叉编码器对 Top-K 逐一打分，区分方向、左右手、顺逆时针等细节
   ▼
结果集（带分数）→ 人工抽看 → 保存为查询结果快照

三条设计要点：

  • 索引粒度是子任务段和演示库切片；整 episode 粒度只用于去重。
  • 去重 embedding 和检索 embedding 分开：去重只要"像不像"，检索要能分清动作细节——"拧开"和"拧紧"在去重眼里一样，在检索里必须不同。
  • 存储沿用 pgvector 起步，规模超过约 1e7 向量换 Milvus/Qdrant。

11.5 模型选型与验收

  • 基线：SigLIP 帧特征聚合（已是去重默认）。
  • 候选：Qwen3-VL-Embedding（召回）+ Qwen3-VL-Rerank（精排）。⚠️ license 与权重开放情况待核查，核查前只进研究分支（U-11）。
  • 验收用自己的标注构造检索基准，不用对方的案例数字：从打标结果自动生成"成对难查询"——同任务但方向相反、左手 vs 右手、成功 vs 失败——看 Top-K 召回率和精排后 Top-1 正确率。

这把尺子有个附带好处：它同时检验打标槽位的质量。如果检索分不清左右手，可能是 embedding 不行，也可能是 hand 槽位标错了。

一个外推警告：车企 corner case 案例的召回准确率（22 个标签平均 70%+，自报 ⚠️）是驾驶图片场景，不能外推到操作视频。

11.6 查询即配置

  • 保存的查询是版本化文件（提议 configs/queries/<name>.yaml）：查询文本或示例片段引用、结构化条件、召回与精排模型版本、Top-K、阈值。
  • 查询结果快照（片段清单 + 分数）写入 lineage；训练集 manifest 可以引用查询快照，查询哈希随配方哈希一起进训练 run 的 lineage。

这样"这批训练数据是怎么挑出来的"可以复现，也能被删除请求沿链追到。

11.7 模块归属

提议 src/fdp/curation/mining.py，CLI fdp curate --stage mine（建索引）与 fdp curate --query <name>（执行查询、产出快照），待 U-48 裁决。不单开管线层：挖掘读的是 curation 的产物、写的是 curation 的决策与快照，归 curation 层最自然。

11.8 本章小结

  • 去重两层阈值：近重复留最好的一条，语义重复只降权。
  • 再平衡四轴聚类，稀缺簇触发采集配额，过剩簇降权，温度采样是消融参数。
  • 挖掘 = 结构化过滤 + 召回 + 精排；去重与检索用不同的 embedding。
  • 检索验收用成对难查询，同时检验标注槽位。
  • 查询即配置：版本化、快照进 lineage、manifest 可引用。

第 12 章 数据集构建：从标记到可训练视图

前面所有环节都在"追加标记"。到了数据集构建这一步，要把这些标记兑现成一份冻结的、可复现的、可被模型直接读的训练集。这一章讲统一槽位向量、LeRobot v3 映射、QC 视图、manifest，以及评测集的固定与泄漏防护。

12.1 输入与步骤

data-pipeline-design.md §8：

  • 输入：策展决策（哪些 episode 处于 training_ready）、配方（configs/mixtures/*.yaml）、可选的查询快照、标注档案。
  • 步骤：可训练性检查 → 按配方采样 → 按档案组装标注 → 导出 LeRobot v3 与演示库切片 → 生成冻结的 manifest。

12.2 统一槽位向量

四轨数据的状态和动作维度各不相同。本仓库用固定布局的槽位向量 + 二值有效掩码统一它们（data-format-contract.md §2.3，slot_layout_version = 1），单位 SI，姿态用 3D 位置 + 6D 旋转：

段 维 内容
joint_pos 32 关节角，按具身档案顺序，不足补 0 + 掩码
ee_pose_left / ee_pose_right 9 + 9 末端位姿（相机系或基座系，frame 元数据声明）
gripper_left / gripper_right 1 + 1 开度 [0,1]
hand_left / hand_right 16 + 16 灵巧手关节
base_vel 3 vx, vy, ωz
head_pose 9 头部位姿（human/device 轨的相机自运动）

合计 96 维。动作段同布局，以相机系增量为主。RDT 的 128 维与某大模型厂商的 80 维是同一思路。

为什么用掩码而不是每具身一个头：GR00T 式的每具身独立 MLP 头与"新增采集形态 = 新增 track 值不改 schema"的哲学冲突；掩码槽位更干净，新具身零架构改动（training-pipeline.md §1.3）。

兼容视图：同一数据集另导出 π0 兼容视图（原生维度 + 零填充到 32 维），让 M1 导出即可用 openpi 微调，这是 Stage A 的前提。

12.3 LeRobot v3 映射

LeRobot v3 一个数据集只有一个 fps。规则：主表 fps = 动作/状态率（robot 默认 100，device = 传感器原生率，human = 伪标签输出率，默认 30）；视觉流按原生 fps 存 mp4，取帧用最近帧并记录 Δt。

主要列：

列 说明
timestamp / fdp.timestamp_ns 秒（LeRobot 必需）/ 纳秒（无损，跨数据集对齐用）
observation.images.<camera> 语义名；fdp.image_dt_ns.<camera> 记取帧 Δt
observation.state / state_mask 槽位向量与掩码
action / action_mask 动作槽位与掩码
fdp.raw.<stream> 不进槽位的流原样带出（如触觉阵列）
fdp.intervention 该帧处于人工接管中
fdp.subtask_index 子任务索引，−1 = 无
fdp.quality_score episode 级质量分

episode 级元数据全量 JSON 写进 meta/episodes/*.parquet 的 fdp_meta 列；子任务指令与区间在 meta/fdp_subtasks.parquet。

另有可选的连续时间事件流视图：每条消息一行 (timestamp_ns, stream, values)，不对齐到任何 fps。它是"schema 不预设消费架构"这一宣称的可验证形式（U-12）。

12.4 训练态加工

curation-pipeline.md §5：

  • 分辨率阶梯：原始存档 / 训练 448p–720p / 预览 320p。GR00T 2 的经验是训练消费的是低分辨率、低帧率的连续窗口，存储要分层；按末端类型分档的分辨率与帧率是后续优化（行动清单 #8）。
  • 归一化统计：按（track × 具身）分开的分位数统计，1%/99% 截断归一化优于 min-max；统计文件随 dataset_version 走，只在 QC 视图保留的样本上计算。
  • 增强不落盘：颜色抖动、裁剪在 dataloader 做，存储永远保持原样。

12.5 QC 视图：标记不删除在训练态的落地

这是 2026-11-18 从 GR00T 2 回灌的关键机制（curation §5）：

  • 各门的判定结果作为列追加到 episode / 步级指标表，不改写原数据，也不在 dataloader 里实时过滤。
  • export 时按（数据集版本 × quality_rule 版本 × 训练配方的窗口长度）离线生成一份"合格样本起点"视图，写成 manifest 的一部分，连同该视图上算出的归一化统计一起进 lineage。
  • 新增一个门 = 新增一列 + 重建视图，不重写已有列。

结果是：同一份数据可以同时存在多个视图，消融只是换视图。这就是第 8 章"阈值由消融裁决"在工程上可行的原因。

12.6 可训练性检查

export 前单独出报告，作为与完整性、有效性并列的独立质检维度：统一坐标系与单位、相机系→世界系变换约定、MANO 拓扑与关节定义一致、state/action 维度与槽位布局对齐、抽帧与编码规范、schema 与标注版本可追溯。任何一项不过，该 episode 不进训练分片，只标记。

12.7 分片、幂等与增量

  • 分片按（track × 任务簇 × 质量层）组织，每 shard ≤2 GB parquet + 对应 mp4；meta/fdp_shards.parquet 记录每 shard 的 episode 与内容哈希。
  • 幂等键：(dataset_version, episode_id, content_hash)。重跑时哈希一致的跳过，不一致的整 shard 重写并 bump dataset_version。
  • 增量：新 episode 追加为新 shard，旧 shard 不改。
  • writer 抽象成接口（ExportWriter），LeRobot v3 是默认实现，对 lerobot 核心包的依赖限定在该实现内（R-10）。

12.8 manifest

冻结的 manifest 包含：episode 清单与内容哈希、配方哈希、查询快照哈希、标注档案与规范版本、split_version、合成数据占比、QC 视图。它对应 lineage 的 datasets / dataset_episodes 表。

有了 manifest，"这个模型是用什么数据训出来的"就有了唯一答案。

12.9 评测集固定与泄漏防护

curation-pipeline.md §8：

  • held-out 在 ingest 后、curation 前就固定：按 scene_id 与 operator_id 做组切分（同一场景、同一操作者不跨 train/held-out），比例 5–10%，写入 split 并版本化；曾进入 held-out 的 episode 永不回流训练集。
  • M1 期 curation 还没实现时，export 层用同一组规则生成 held-out 清单文件——机制不等 M2。
  • 去重与再平衡只在 train 池内做；演示库切片不得取自 held-out；合成种子不得取自 held-out。
  • 泄漏检测：训练前跑 train↔held-out 的近重复检查（余弦 >0.95 视为泄漏，从 train 剔除并记录）。

为什么要在 curation 之前固定？因为如果先策展再切分，再平衡的聚类统计就已经"看过"了评测集，评测结果会系统性偏高。

12.10 本章小结

  • 96 维槽位 + 掩码统一四轨；同时出 π0 兼容视图。
  • 主表 fps = 动作率，视觉按原生率，取帧记 Δt。
  • QC 视图：判定是列，视图离线生成，消融只是换视图。
  • 可训练性检查不过只标记、不进分片。
  • manifest 钉住数据、配方、查询、标注版本、切分版本。
  • held-out 入湖即固定、组切分、永不回流，训练前查泄漏。

第 13 章 训练如何消费数据

这本书讲的是数据管线，不是模型。但数据管线的每一个设计——分层采样率、槽位向量、相机语义名、帧对导出、奖励列——都是为某种训练消费方式准备的。这一章从数据的角度看训练层：模型要什么，数据层要为此做什么。训练层本身的设计在 training-pipeline.md，不在本仓库实现（fdp-policy 独立仓库）。

13.1 原则：数据引擎优先，模型设计保守

每个模型决策抄已被 ≥2 家独立验证的共识，创新预算全部留给数据层。理由来自"规模换参数"的证据：Octo 93M 训 80 万演示 ≈ RT-2 55B；OpenVLA 7B 训 97 万 OXE episode > RT-2-X 55B（论文）——中等模型 + 大而多样的数据集是可行的开源路线。

注意 Stage A 的定位：它不是为了得到好模型，而是证明数据层无毒。一条管线可能每个环节都"看起来对"，但只要相机名映射错了一处、归一化统计算错了一处，微调就会比零样本还差。Stage A 是对整条 M1 管线的端到端验收。

13.7 数据配方是一等公民

configs/mixtures/*.yaml 声明各轨、各任务簇、各质量层的采样权重与温度，配方文件哈希进训练 run 元数据。任何模型都可以回溯到确切的数据配方。

配方的结构（roadmap L6 与 GR00T 2 的启发）：

  • 按 track、source、embodiment 设份额；
  • 合成数据按 source 单独成组；
  • play 数据单独成组；
  • 目标域 ≤5%，广度优先（Stage B）；
  • 元数据条件化：低质、失败、自主 rollout 数据带标签入训练。

汇率问题：人类视频一小时顶几小时遥操作？GR00T 2 只证明了人类视频的边际收益为正，没给出换算。任何按他家配比照搬预算的做法都没有依据，只能靠我们自己的换算率实验（U-40）。

13.8 自建工具：数据引擎的方向盘

training-pipeline.md §3.2 的五个自建工具（M3 交付）：

  1. mixture-runner：读配方 → 构建混合流式数据集 → 提交训练 → 登记 lineage。消融 = 多配方并行。
  2. scaling-fitter：对消融结果拟合 L(D) = (D_c/D)^α，加按场景/物体/操作者切分的多样性幂律检验，输出"下一小时数据该采什么"的预算建议。这是数据引擎的方向盘。
  3. fewshot-bench：从演示库抽 1 条 / 5 分钟数据，做零梯度 in-context 与 10 步微调两种评测——比全量微调更灵敏的数据质量探针。
  4. reward-trainer：从 QC 标记批量训练任务奖励分类器，Stage D 与 L3 语义审计共用。
  5. eval-CI：checkpoint 触发的仿真回归 + 指标仪表盘 + 真机协议模板。

13.9 工具链版本的教训

第 14 章 评测与回流闭环

数据飞轮转没转，只有一个证据：数据改动之后，评测涨了没有。 这一章讲评测的口径（什么叫"显著优于"）、checkpoint 的排名方法、仿真与真机的关系、车队回流，以及把这些串起来的回流闭环。

14.1 诚实性协议

先讲为什么评测要设计得这么严。Figure 的关键宣称有第三方反驳先例：BMW 曾公开反驳其部署宣称（单台、非生产时段 vs "每天端到端运营"）；81 小时分拣直播被质疑有遥操作痕迹（第三方，architecture.md §4）。

所以本仓库的评测协议要求：可复现日志 + 干预率记录，杜绝"零干预"式不可验证宣称。对外任何能力宣称必须能指向一个 run_id 及其日志。

14.2 指标字典

eval-protocol.md §1 是本仓库所有"显著""达标""收益"的唯一定义。

数据侧：通过率漏斗、可用训练小时、每可用训练小时全成本、多样性计数（按词表版本报）、伪标签质量、同步残差 P95、欺诈检出率。

模型侧：

指标 定义
成功率 任务模板完成判据为真的 trial 比例，一起报 95% Wilson 区间
任务进度分 子任务完成数 / 子任务总数的均值
介入率 接管次数 / 自主运行小时；接管时长占比
吞吐 每小时完成任务数（营业级指标）
少样本适应 三个刻度并列：1 条演示零梯度；1–5 分钟数据 10 步微调；≤10 h 全量后训练
OOD 分轴 背景 / 光照 / 物体 / 场地四轴各自的成功率下降

规模侧：L(D) 拟合报 α、D_c、R²，数据每翻倍重拟合；多样性幂律按场景数、物体数、操作者数各自拟合。

14.3 消融判定规则

  • 单位：一次消融 = 同一代码 commit、同一超参、只变一个因子。
  • 显著性：仿真 ≥3 seed，报均值 ± 标准差；真机每任务 ≥20 trial；Fisher 精确检验（成功率）或 Welch t（进度分），α = 0.05；效应量至少 5 个百分点才算收益。
  • 功效预估：20 trial 检测 25 个百分点差异的功效约 0.8；检测 10 个百分点需 ≥80 trial。报告必须注明本次功效。
  • Stage A 放行：仿真自建任务集上微调后成功率 − 零样本 ≥10 个百分点且 p < 0.05，3 seed。
  • Stage B 止损：0→1 预训练模型不低于 Stage A 微调对照（差 <5 个百分点视为持平，持平不放行）。
  • 阈值裁决：严格化后指标不涨（<5 个百分点且不显著）一律回退。

功效这一条特别重要。20 trial 的真机评测只能检出很大的差异；如果报告说"A 和 B 没有显著差异"，而功效只有 0.3，这个结论几乎没有信息量。

14.4 真机协议模板

每次真机评测填写并存档 data/eval/<run_id>/protocol.yaml：策略与基线的 checkpoint、数据集版本与配方哈希；具身与固件；每任务 ≥20 trial、ABAB 交替、操作员盲测；≥3 个场景且至少一个 held-out 场地；种子化物体摆放（照片存档）；成功判据版本；接管策略；MCAP 全量记录且 rollout 回流入湖；报告成功率 + Wilson 区间、进度分、介入率、吞吐、失败案例视频索引。

14.5 checkpoint 排名：盲测 A/B + Bradley-Terry

绝对成功率会随采集站、操作员、硬件和日期漂移，不同场次的数字不能直接比。挑 checkpoint、比配方时要回答的是"哪个更好、好多少、有多确定"。做法参照 NVIDIA GearArena（自报 ⚠️，eval-protocol §3.1）：

  • 一次 trial：同一场景、同一操作员、几分钟内，以随机顺序跑 2–4 个 checkpoint，操作员不知道哪个是哪个，给出排序。漂移由同组共享，在比较中抵消。
  • 评分：所有成对比较拟合 Bradley-Terry，换算成 Elo；每个任务等权；置信区间按任务重采样 bootstrap（独立单位是任务，不是 trial）。
  • 接入：新 checkpoint 先和当前榜首对打，保证评分在一个连通的尺度上。
  • 任务集维护：所有 checkpoint 都能完成的任务归档，都完成不了的搁置——两者都不区分模型。
  • 边界：GR00T 2 报告 30–35% 的比较是平局，任务少时区间很宽，报告必须注明比较数和任务数。

14.6 仿真：相对比较可以，绝对能力不行

基准 用途
LIBERO（四套件） 每 checkpoint 回归；社区可比
SIMPLEREnv real-to-sim 一致性
Isaac Lab-Arena 自建任务集（与真机任务模板一一对应；场景用 SimFoundry 从真机评测场地视频重建） 消融主战场
RoboTwin 子集 双臂
长任务规划基准（SimFoundry 孪生 + BDDL 逐步校验 + 扰动） S2 规划

仿真基准用的具身与目标本体不同（LIBERO 是 Franka），所以仿真结论只用于相对比较（配方 A vs B），绝对能力以真机为准。

sim-real gap 探针与相关性门

  • 同任务的 teleop_replay 与真机 episode 比轨迹 RMSE 与成功率差；gap >20 个百分点的任务簇标"仿真不可信"。
  • 场景级保真度：同一组策略在孪生场景与真机各跑 ≥20 trial，报 Pearson r 与 MMRV。SimFoundry 论文值 0.911 / 0.018；我们的门槛 r ≥0.8。
  • GR00T 2 用 14 个 checkpoint 标定后，仿真与真机的进度、成功率、Elo 的 Pearson r 在 0.92–0.93（自报 ⚠️）。标定后仿真承担三件事：checkpoint 追踪与候选收窄、数据管线改动的回归（loader、配方改动先跑小规模训练 + 闭环仿真）、推理设置初筛。三项都过门槛的任务簇才允许用仿真替代真机做这三件事；最终放行仍以真机为准。

图 3（引自 data-strategy-roadmap §1.5）　评测三层代理与各自的可信度：真机是真值但每 ±2 点需约 1,030 次试验；仿真孪生用每任务约 10 条真机演示校准；世界模型代理与真机相关最高 0.989，但只在专家动作分布内有效。代理相关性连续两季度 <0.8 即回退真机（G4）。

14.7 车队回流

部署中的机器人用同一个 recorder 记录自主 rollout（source="fleet"，policy_version 与 deployment_id 必填），回坞批量卸数（robot-track-teleop.md §6、runtime-and-deployment.md §3–§4）：

  • 带宽有限时的优先级：含接管、OOD、失败的 episode 优先上传；成功 episode 抽样 20%。
  • 用途优先级：奖励分类器素材 > 纠错片段（接管前后各 5 s）> 成功 rollout 进 SFT；失败 rollout 不进 SFT，只进 RL。
  • OOD 事件：动作块一致性差、观测 embedding 偏离训练分布、任务进度停滞、力/触觉超限，任一触发即记 /event/ood，与接管一起对齐到 episode 时间轴，是 RL 闭环的负样本来源。
  • 再训练触发：接管率周环比上升 >30%，或某任务簇成功率跌破阈值 → 开经验后训练 run（Stage D）。
  • train/serve skew 的三大来源（相机语义映射、归一化统计、分辨率阶梯）全部由 export 产物驱动，不在运行时手写。

干预段是最贵的对齐层数据：只在自家部署中产生，没有厂商公开干预率。在车队到位之前，用配对集 + DAgger 替代，首批部署当采集车队而非收入来源（roadmap §2.5）。

14.8 回流闭环：一轮的步骤

这是 2026-11-17 新增的跨层流程（data-pipeline-design.md §9）：

触发：评测报告 或 车队回流（干预、失败、OOD 事件）
  1. 失败归类：每个失败片段按失败模式词表打标
  2. 反查：用失败片段做挖掘查询，看训练集中相近样本的数量和质量
  3. 诊断，三选一或组合：
       数据少          → 采集配额（下发采集任务，带 collection_rule）或合成种子
       数据有但被过滤  → 检查对应阈值是否过严（走消融，不直接改）
       数据有但标错    → 打标规范待裁决 + 重映射
  4. 生成新数据集版本，写 manifest
  5. 再评测：按统计判定规则比较前后版本
  6. 评测不涨 → 本轮数据改动回退

第 3 步是整条闭环的核心：失败的原因只有三种——缺数据、数据被误杀、数据标错，每种对应管线的一个不同环节。挖掘（第 11 章）就是做这个诊断的工具。

图 4（引自 data-strategy-roadmap §1.6）　车队数据飞轮：部署机器人在 OOD 探针触发下录制干预段，经段级策展与估值进入 DAgger / 车队 RL，新 checkpoint 过评测 CI 再部署。

14.9 loop 记录

每一轮写一条 loop 记录：触发来源、失败归类统计、执行的查询与快照、采取的动作（配额 / 合成 / 重加权 / 重标）、产出的数据集版本、评测前后对比、结论（保留 / 回退）。对应 lineage 的 loops 表。

这条记录是"数据飞轮转了没有"的唯一证据，也是向管理层汇报数据投入产出的依据。数据系统的"闭环有效率"指标 = 评测提升的轮次 / 总轮次。

节奏：M3 起按评测节奏运行（每个配方 A/B 周期一轮）；单任务部署场景（如洗衣分类大脑的每周难例集）可以更快，但走同一记录格式。

14.10 本章小结

  • 诚实性协议：可复现日志 + 干预率；对外宣称必须能指向 run_id。
  • 显著性看 Fisher/Welch + 效应量 ≥5 点 + 功效声明。
  • checkpoint 排名用盲测成对比较 + Bradley-Terry，按任务 bootstrap。
  • 仿真只做相对比较；过了相关性门才能替代真机做回归和初筛。
  • 车队回流：失败与接管优先，失败不进 SFT 只进 RL。
  • 回流闭环：失败归类 → 反查 → 缺数据 / 被误杀 / 标错三选一 → 新版本 → 再评测 → 不涨就回退；每轮一条 loop 记录。

采集 → 可训练时延 P50 ≤3 天，P95 ≤7 天
质检一致性（同一样本重跑结论一致） ≥98%
死信队列 0 积压 >24 小时
欺诈红队检出率 ≥95%
删除请求完成 30 天
闭环周期 一个配方 A/B 周期内

"质检一致性"值得单独说：如果同一条数据重跑两次质检结论不同，那么所有基于质检的消融都没有意义。VLM 的非确定性让这一条并不容易做到。

15.7 自建与采购

自建：状态机、质检规则、标注规范、查询、配方、lineage 语义、模型网关。这些是资产不贬值、可迁移的前提。

采购或开源：对象存储、元数据库（PostgreSQL）、向量库（pgvector → Milvus/Qdrant）、编排（Prefect/Dagster）、批计算（Ray）、标注界面、可视化（rerun、Foxglove）、训练算力。

底座是采购问题，不是设计问题（data-pipeline-design §11）。如果业务方要求数据不出其云，可以把存储、调度、批计算、训练托管到云厂商，本仓库的模块作为其上的作业运行——前提是确认数据导出能力、lineage 能否完整记录、成本，以及闭源合成平台的三问（第 10 章）。裁决见 U-49。

15.8 运营与组织

  • 不设"数据标注团队"：标注走 VLM 初标 + 分层人工抽检 + 外包审核员，避免形成固定成本中心（roadmap §4.3）。
  • 人工编制估算（H1，1,000 小时/月入湖）：欺诈灰区 2 人、L2 尾部 + 分歧样本 2 人、金标准抽检 1 人，共约 5 人/千小时·月，随信誉体系成熟下降（curation §9）。
  • 审核员一致性（Cohen's κ）每月抽测，<0.7 重训指南；审核员只看脱敏预览流，raw 不进审核台。
  • 数据引擎按四个组组织：数据平台与契约、策展与对齐算法、评测与闭环、采集与 Creator 运营；评测负责人先于采集扩张到岗（U-27）。

15.9 本章小结

  • 九个子系统，新增任务下发、模型网关与注册、数据服务、人工作业台。
  • 八类数据产品各有 owner、版本规则和服务水平。
  • lineage 是骨架：模型升级不改历史决策，删除沿链传导。
  • 所有规则都是版本化文件。
  • 容量的新变量是 VLM 调用和向量索引；未知的算力口径先实测。
  • 逻辑自建、底座采购；不设固定标注团队；评测先于采集扩张。

第 16 章 合规、安全与治理

具身数据比互联网数据更"私密"：它在别人的家里、办公室里、厨房里录下来，里面有人脸、有旁观者、有家居布局、有声音。"隐私是生存问题"（index-replica-plan.md §0）。这一章讲本仓库怎么把合规做成管线的一部分，以及怎么用治理登记管住设计里的不确定性。本章不是法律意见，每个区域上线前需法务出具意见（R-01 / R-11）。

16.1 "raw 永存"的准确表述

决策四说 raw 永存，隐私脱敏除外。准确的表述是（compliance-and-security.md §6）：脱敏后的原始 episode 永久保留，除非法律或数据主体要求删除。

数据 保留 例外
raw（脱敏后存档） 永久 撤回或删除请求、未成年人、违法内容、区域法规强制
raw 脱敏前帧哈希 90 天 审计用
原始音频 30 天 口令转写文本永久
Creator 身份与支付 关系终止后按财税法规（通常 5–7 年）
审核台记录 3 年
中间产物 90 天（可重算）

16.2 区域矩阵

实现：EpisodeMeta 的 region 字段决定 bucket 区域与合规开关集（人脸处理方式、保留期、删除 SLA）；跨区训练只用已脱敏的 training 区数据，raw 不跨区。

2026 下半年的监管叠层让这件事从"合规成本"变成了"交付条件"：欧盟 Data Act、CRA、PLD、机械法规（2027-01-20 起适用）的叠层，以及中国 YD/T 6771-2026 八维数据质量标准（2026-11-01 实施）都要求机器可读的来源、同意与生命周期记录（data-strategy-roadmap.md §1.7）。

16.3 同意与旁观者

Creator 协议要点：

  • 授权范围覆盖训练、评测、衍生数据集（含具身转换等派生产物）；对外发布数据集需单独勾选；
  • 撤回后 30 天内从 raw / curated / training 删除；已训练完成的模型不回滚，但记录在案，后续数据集版本剔除——必须在协议明示；
  • 按通过策展的分钟数计酬，费率与信誉分级公示。

旁观者与未成年人：

  • 端上：硬连线录制指示灯 + App 强提示；可选端上人脸模糊；
  • 入湖强制：人脸检测 + 模糊（EgoBlur，Apache）；检出未成年人特征的 episode 进人工审核，确认后整段拒收并从 raw 删除——"raw 永存"的合法例外之一；
  • 误模糊：脱敏前帧哈希留存 90 天供审计，误模糊率进 QC，误模糊的 episode 标 flag:overblur，不删除；
  • 语音：环境音频默认不入训练集，仅口令段附近 ±2 s 保留转写文本。

家居 3D 孪生（Creator 场景扫描经 SimFoundry 重建的物体清单、布局、网格）视为敏感个人数据：入网时单独勾选同意；按 region 驻留、不对外发布；随 Creator 删除请求一并删除，并传导到由其派生的 sim 轨 episode（parent_episode_id 链）。

16.4 删除传导

删除是 lineage 设计的最终检验。流程（compliance §4）：

deletions 表登记 → raw → curated → training → 数据集 manifest 剔除
                → 派生 episode（转换、合成、增殖、孪生）沿 parent_episode_id 链删除
                → 受影响的 training_runs 登记（模型不回滚）

SLA 30 天，第 21 天未完成告警；每季度随机抽查删除请求是否真的删干净。查询快照引用的片段同样在传导范围内——这是"查询即配置、快照进 lineage"的另一个用处。

级别 内容 访问

16.6 安全基线

  • 设备：固件签名 + 安全启动；OTA 签名包与灰度；本地存储加密，密钥与账号绑定，丢失可远程吊销。
  • 端点：设备证书 + 短期 token；无证书上传直接拒绝。
  • 投毒防御：新账户全量审计；跨账户 embedding 碰撞；红队植入测试；训练前 held-out 泄漏检查；单账户短期大量高相似上传自动冻结。
  • 供应链：依赖锁定（uv.lock）、镜像签名、模型权重哈希校验。

16.7 license 纪律

模型和资产的 license 是一个容易被忽视、一旦出事就很难补救的风险。本仓库的纪律（cleaning-algo-selection.md §2）：

  1. 每个模型的版本与权重哈希进 lineage——模型升级 = 数据世代切换，必须可追溯；
  2. ⚠️ 待核查项在 M2 策展实现开始前完成 license 终审；非商用许可的模型只允许出现在研究分支（DOVER、FAST-VQA、pyiqa 等）；
  3. 所有 AI 判定阈值与传统阈值一样服从消融裁决；
  4. 商业 API 没有权重哈希，改记模型名 + API 版本字符串 + 调用日期，其服务条款对"输出用于训练数据"的许可属于终审范围。

几个具体例子：UMI 原配的 ORB-SLAM3 是 GPLv3，只允许服务端处理、不得进设备固件或分发件，商用发行前须切到 BSD 的 Basalt 或完成合规评估（U-10）；SimFoundry 本身 Apache-2.0，但默认安装链含非商用组件，进默认路径前要换件（U-20）。逐项核查状态在 governance.md 的 U-11 表。

一个设计里充满了"暂时这么定"。governance.md 用三张活表管住它们（截至成书日约 29 条风险、51 条未决决策、34 条自报数字）：

17.5 尚未解决的问题

最后列出几个连领先团队自己也没解决的问题。它们决定了本书描述的很多设计只能是"带探针的假设"。

汇率

人类视频一小时顶几小时遥操作？GR00T 2 只证明人类视频的边际收益为正，没有给出换算；人类视频缩放曲线每档只训一次，1%→10% 在噪声内（gr00t2-trends-analysis.md §5）。任何按他家配比照搬预算的做法都没有依据。只能靠 U-40 的换算率实验自己测。

伪动作的上限

人类视频丢了主动感知；生成视频"几何幸存、控制信号丢失"。GR00T 2 的人类视频收益主要来自视频预测损失，动作损失依赖手部位姿精度——这层精度在我们这里还没有基线。伪标签金标准抽检（第 10 章）是第一个探针。

触觉与力

人类视频不含触觉与力反馈，Index 类数据能撑多深的接触密集操作未被证明（architecture §6）。残差 RL 的力觉变体在接触密集任务 50%→93%（论文）说明力信号有价值，所以契约 0.3 预留了力类动作槽位、D1 规划了触觉 UMI 对照集——但"需要多少触觉数据"仍是开放问题。

自动验证不可靠

拧到一半的螺丝被模型和 agent 都判为完成（GR00T 2 自述）。标注引擎化、agent 质检、世界模型评测器都有同一个盲区：它们在专家分布外的判断不可信。所以本书反复强调保留人工金标准审计，不能完全去人。

灵巧度与端侧压缩的冲突

GR00T 2 的压缩版在灵巧手上掉一半成功率（自报 ⚠️）。"端侧够跑"只对夹爪类任务成立；灵巧手上机的延迟和精度仍然要折中。这会反过来影响数据：如果部署模型必须压缩，训练数据的分辨率、帧率、动作块长度可能都要按末端类型分档。

宣称的可信度

最后，也是最朴素的一条：行业里的数字大多是自报的，有第三方反驳的先例。架构设计不能按宣传口径过度乐观。治理表的 D 栏、"若不成立"分支、评测的诚实性协议，都是为此准备的。

17.6 全书小结

如果只记住一页，记住这些：

  1. 瓶颈不是"采不到"，而是"对不齐、验不了、用不上"。原始小时是输入，不是资产。
  2. 七条决策：双格式、四轨同 schema、分层采样率、策展五阶段、AV1 + yuv420p、质量优先、训练保守。
  3. 时间对齐只用 publish_time，误差预算以一个控制周期为界，标定随数据走。
  4. 清洗是标记不是删除；标记变成列，训练选视图，消融只是换视图。
  5. 质检先交付：规则段零模型、语义段先粗后细、报告是交付物。
  6. 先定边界再写描述；两把尺子；描述槽位化；标注是可重算的派生物。
  7. 合成由挖掘驱动、按 source 成组、评测集永不含合成数据。
  8. manifest 钉住一切版本；held-out 入湖即固定、永不回流。
  9. 评测口径先于结论：Wilson 区间、效应量、功效、按任务 bootstrap。
  10. 回流闭环只有三种诊断：缺数据、被误杀、标错；每轮一条 loop 记录，不涨就回退。
  11. lineage 是骨架：可复现、可消融、可删除，三者同源。
  12. 不确定性要登记：风险、未决、自报数字，每条有 owner 和"若不成立"。
